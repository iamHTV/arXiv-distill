# 2608.04270v2 CURATE: Leveraging LLM Agents to Compose, Catalog, and Deploy Reproducible Workflows

## Problem
- Agentic code generation can accelerate computational workflow development, but coding agents (Claude Code, Codex) focus on code generation and do NOT address the entire workflow lifecycle, including deployment and sharing — users must develop and stitch modules independently while managing deployment themselves.
- Prior work: LLM4Workflow composes multi-step workflows without reuse; Thareja et al. apply skills to workflow generation without catalog storage/retrieval; Lee et al. use HITL + module reuse via RAG but only for Excel/CSV data-cleaning; WorkflowHub/CWL provide registries/languages but no automatic component reuse during composition.

## Contribution
- CURATE (Composition, User-in-the-loop, Reuse, and Automated Task Execution): a human-in-the-loop multi-agent system using LLM agents to manage and develop composable workflows across their entire lifecycle, from composition to deployment and reuse.
- A catalog for storage and reuse of modules across workflows — entries hold ID, name, natural-language description, inputs/outputs, PyPI dependencies, secret names (not values), rank, keywords, provenance (source workflow), usage count; BM25 index on keywords with the tokenized WCA skeleton description as query; a foundation for FAIR principles (Findable, Accessible, Interoperable, Reusable).
- Feasibility demo: open-source 6,700-line Python prototype (LangGraph coordination, Claude Opus 4.8, MGA via Claude Agent SDK) + 6 experiments (4 from the SeBS-Flow serverless benchmark suite + 2 real-world PyADM1 anaerobic digestion simulations).

## Method
- Workflow model: nodes (computational tasks) + edges (control dependencies); task precedence must be a DAG known ahead of runtime scheduling; modules implemented as Python functions (function-granularity, task-driven, file-transported).
- 4 agents: WCA (Workflow Composition Agent — controls structure, generates the high-level skeleton in natural language, delegates source resolution, resolves precedence edges with concrete inputs/outputs); MCA (Module Candidate Agent — resolves each skeleton task's source: 1) catalog match, 2) user-provided module, 3) previous workflow iteration, 4) fresh generation by MGA; uses an LLM call with the user request, WMS description, and previous revisions as context); MGA (Module Generation Agent — coding agent generates/adapts modules, tests locally in a scratch directory, skips nodes reused from catalog/previous revisions, ensures I/O matches the skeleton); WDA (Workflow Deployment Agent — deploys and continually monitors artifacts, spawns a post-run chatbot agent giving an NL summary, Q&A via MCP tools to download artifacts/view logs, and revision suggestions).
- 9-stage LangGraph pipeline, 5 HITL gates: Gate 1 Skeleton (WCA sketch; user provides modules + context such as PDFs, example I/O, markdown); Gate 2 Resolution (WCA fills edge descriptions → MCA resolves sources → WCA fills concrete dataflow file names + likely PyPI dependencies; user approves); Gate 3 Generation (MGA topological sort, sequential traversal, each function in its own scratch directory with a CONTEXT.md — user prompt, data integrity requirements, FaaSr testing stubs — plus a per-function file: description, signature, I/O files/dataflow, dependencies, secret names; a single coding-agent session, one function per turn, validated against local stubs before moving on; user scrolls code + workflow file); Gate 4 Deploy (FaaSr → GitHub Actions; trivially targets AWS Lambda, OpenWhisk, SLURM, GCP, Kubernetes); Gate 5 Post-run (WDA chatbot: NL summary, Q&A, revise, commit functions to the catalog, save workflow; on failure reviews artifacts/logs and advises an adaptation).
- Function labels: [New], [Catalog], [Cache] (implemented in an earlier revision cycle), [User Provided Module], optional [Adapt] (use an existing function as context but adapt it). [Catalog]/[Cache] nodes are skipped by the MGA unless [Adapt]. [User Provided Module] without [Adapt]: the MGA wraps it with FaaSr I/O stubs for S3 retrieval/storage without changing the module's code, constructs synthetic data, and runs local parity checks. The MGA is instructed not to return an implementation until it has tested with real data (where available), public API data, or local synthetic data. The FaaSr workflow JSON is created deterministically by a tool (not an agent) translating the skeleton to the schema; extra dependencies discovered by the MGA go to a manifest merged into the workflow config.
- Revision: an LLM classifies requested changes as structural (modify the DAG → loop back to the skeleton step) vs functional (modify functions already in the skeleton → loop back to the resolution step).
- Deployment target: FaaSr serverless FaaS WMS (originally R, extended to Python) — schema-defined, task-driven, function-granularity DAG with only conditional branches as dynamicity; serverless simplifies deployment; containerized execution provides isolation. Resource isolation: sandboxed containers/VMs, with care for state isolation in centralized storage to prevent side effects through file I/O.

## Key Findings
- E1 Machine Learning (SeBS-Flow): dataset generation (N=500, M=1024, make_classification weights [0.9,0.1], flip_y=0.1, random_state=123), preprocessing (StandardScaler, train_test_split test_size=0.4), K=2 concurrent classifiers (SVM SVC kernel=linear C=0.025; RF max_depth=5, n_estimators=10, unseeded). Gate 1 revision: split train_classifier into two concurrent functions. SVM accuracy identical; generated RF 0.850 ± 0.002 vs original 0.851 ± 0.006 (60 invocations each). Baseline ✓ 3/3.
- E2 MapReduce: words from [cat, dog, bird, horse, pig] evenly distributed + shuffled; Split → Map → Shuffle → Reduce; word counts matched the SeBS-Flow ground truth verbatim. Baseline ✓ 1/3.
- E3 Video Analysis: Faster R-CNN ResNet-50 COCO (cv2.dnn), 3 external inputs, output {label, class, score} with score>0.5, COCO 80 classes zero-indexed; correctly identified cars (ground truth: car in all frames), no runtime errors. Baseline ✗ 0/3.
- E4 PDF + MapReduce + Visualize: reused 4 functions (split/map/shuffle/reduce verbatim with the original rank per the Gate 2 revision) + 2 new (extract words from words.pdf, visualize); 5 words randomly distributed 100–1500 occurrences; expected word counts matched actual; histogram well formatted. Baseline ✓ 1/3.
- E5 PyADM1 (real-world): 7-step workflow cleaning raw digester influent: convert-units (Q MGD→m³/d, T °F→°C with rename, divide ALL 22 COD columns by 1000, leave S_IC/S_IN/S_cation/S_anion untouched), fill-gaps (forward-fill S_cation/S_anion), remove-spikes (replace isolated spikes in Q and T with the local median), interpolate (26 weekly lab columns → 15-min), validate (validation_report.csv), pyadm1 (dynamic_out.csv), visualize (simulation_plots.png). Synthetic raw data: unit conversions + weekly holds on 26 lab features + 3–7 day gaps in 3 places (S_cation, S_anion) + implausible spikes in T and Q in 4 places each. Result: addressed most changes EXCEPT T spikes — T is hard-coded in PyADM1 so the MGA skipped the T spike fixes; the WDA caught this and suggested fixing the T spikes and modifying PyADM1, but the authors forwent the revision to keep the model unmodified. Baseline ✓ 1/3.
- E6 PyADM1 + concurrency: vary-inputs creates 20 inputs from digester_initial varying SRT (solids retention time); pyadm1 runs 20× concurrently. Gate 5 revision (WDA suggestion): q_ad was hard-coded (178.4674) → set q_ad = V_liq / SRT so the 20 ranked runs produce distinct steady states across a 10–60 day sweep; HITL approved → correct results. Baseline ✓ 3/3.
- Token usage: CURATE is higher than the baseline in some cases (multi-agent overhead), but the baseline showed significant non-determinism in output correctness — many cases produced no correct run and required manual revisions (mapping action names to dependencies instead of function names, splitting an action's code into multiple files, one FaaSr S3 API operation with an incorrectly documented argument name); CURATE needed no revisions beyond the built-in NL HITL feedback. Token usage nearly halved from E5 to E6 despite increased workflow complexity (catalog reuse payoff), with less HITL oversight.

## Actionable Insights
1. Catalog module reuse nearly halved token usage (E5→E6) while improving reliability (reusing verified modules instead of regenerating). Apply: build a personal module catalog for recurring content workflows (data cleaning, formatting, publishing); after each workflow completes, commit its functions to the catalog with description + keywords; new workflows query the catalog before generating anything.
2. The 5 HITL gates catch errors early: Gate 1 catches decomposition errors BEFORE code generation (E1: the WCA merged two training functions into one; the user split them at Gate 1). Apply: never let an agent generate code immediately — require a natural-language skeleton first, approve the structure, then generate.
3. The WDA post-run agent caught bugs the MGA missed (E5: hard-coded T spikes; E6: hard-coded q_ad making the SRT sweep meaningless) — multi-agent separation of duties detects errors a single agent does not see. Apply: after a workflow runs, use a separate agent to review logs/artifacts and suggest revisions; do not let the agent that wrote the code review its own work.

## Assumptions & Limitations
- Conditions: task precedence must be a DAG known ahead of runtime (no dynamic scheduling); modules expressible as functions with defined I/O; a compatible WMS is needed (prototype targets FaaSr; extensible to AWS Lambda/OpenWhisk/SLURM/GCP/Kubernetes).
- Stated limitations: the baseline had NO HITL revision at each step (because Claude Code has no built-in workflow creation and does not follow sketch→reify→test) — the comparison is not fully fair; SeBS-Flow is a performance benchmark, not a scientific workflow suite; the ADM1 workflow is limited to initial data preparation (full end-to-end still needs mass-balance preprocessing, feature engineering, sensitivity analysis, validation); the catalog is a minimal implementation (passive storage, BM25 keyword search — no semantic matching, no FAIR compliance yet); the prototype is feasibility-focused.
- Unstated: multi-agent token overhead not quantified (Figure 3 bars only, no numbers); catalog reuse accuracy (BM25 keyword matching may retrieve the wrong module) not measured; single LLM (Opus 4.8) — behavior with other models unknown; catalog growth → search degradation untested.
