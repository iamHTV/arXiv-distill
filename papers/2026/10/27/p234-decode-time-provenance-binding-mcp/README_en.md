# 2610.31974 Agentic AI Defense: Decode-Time Provenance Binding for MCP

## Problem
- Current provenance defenses attach the trust label when a tool returns TEXT, assuming the payload travels through a text channel. Prior work (NeuroTaint) also declares it does not cover multi-modal/semantic steganography, uses unsigned labels, and audits traces offline instead of blocking at runtime.
- Gap: an attacker hides an instruction inside an email-signature logo (inline cid:/data: URI) using steganography — text scanners see only pixels, and the content becomes an instruction only WHEN a tool decodes it (OCR, stego extractor, metadata parser), laundering it into the trusted control flow of a multi-agent MCP pipeline. Email defenses miss it: antivirus matches malware byte signatures — a valid PNG is not malware; DLP inspects text/URLs/attachments, not inline-logo steganalysis; the payload is inert at the mail layer and only "arms" after decode.

## Contribution
- Cross-modal trust laundering: a realistic, zero-click, invisible attack vector, mapped to OWASP LLM01/LLM02/LLM06/LLM08 and the ASI01/02/06/07 agentic taxonomy categories.
- Decode-time provenance binding: the MCP layer mints an HMAC (keyed-hash message authentication code)-signed Untrusted label exactly when a concealment-reversing tool runs, and independently maintains the provenance lineage of every critical call — blocking calls with untrusted lineage even when a compromised agent presents a valid label for an unrelated trusted value (valid-label substitution).
- Principle: contain, don't detect — do not try to detect that an image carries a payload (an arms race the defender loses against ever-better carriers); assume every decode output is untrusted and contain it.

## Method (core summary)
- D = decode tools (stego extraction, metadata decode, Base64 decode, OCR); C = critical tools (side-effecting sinks: export_secrets, send_email, file write, payment). All tool I/O is mediated by the trusted MCP layer.
- Algorithm 1 MintBinding: binding l = (p, t, tau, pi, delta, sigma); delta = input-dependency IDs resolved by the LAYER (never asserted by the agent); tau = Untrusted iff t in D or some input tau_i = Untrusted (contagious); sigma = HMAC_k(p||t||tau||pi||delta), with key k never leaving the layer; Untrusted bindings are added to a per-context taint set; agents receive only an opaque handle id(l).
- Algorithm 2 EnforceCritical (at the sink): resolve handles via the ledger into a transitive dependency closure S; block if sigma fails HMAC recomputation (forged/stripped), if tau = Untrusted in S (untrusted data lineage), if a dependency is unresolved, or if taint(c) minus promoted(c) is non-empty (untrusted context lineage); otherwise allow.
- Invariant (conditions): key confined to the layer; all concealment-reversing tools registered in D; the layer mediates every critical call and inter-agent message (fully mediated context) -> no critical call executes with Untrusted lineage unless an audited trusted promotion cleared it.
- Testbed: a real FastMCP server over stdio, Qwen2.5-0.5B-Instruct running locally; attack bank of 24 payloads = 3 carriers (LSB ~76 dB PSNR/SSIM ~1.000, DCT ~18 dB/SSIM ~0.94, lossless Base64 PNG metadata chunk) x 8 evasions (plain, benign-worded, Base64, token-split, Cyrillic homoglyph, zero-width, Unicode-confusable, HTML-comment wrapping).

## Key Findings
- ASR (Attack Success Rate) over 24 payloads: undefended 100% (24/24 leaks); keyword/DLP scanner 62.5% (15/24); regex parser 62.5% (15/24); in-process taint baseline 0% within one trust domain; decode-time provenance binding 0%. Scanners only stop plain/HTML-comment/confusable variants (Unicode normalization recovers them) and fail on benign-worded/Base64/token-split/homoglyph/zero-width evasions.
- Valid-label substitution: a verifier trusting the agent-supplied binding allows (leaks); layer-maintained lineage blocks when the dependency is omitted and when it is in the arguments; a clean context still allows the legitimate call.
- Four-component ablation: the full mechanism blocks all three attack classes (honest, substitution, forged relay); removing decode marking leaks everything; removing sink mediation leaks everything; removing HMAC still blocks in-domain attacks but leaks the cross-domain forged relay (a remote verifier has only the signature); removing lineage tracking still blocks forgery but leaks substitution (a genuine Trusted binding from an unrelated tool passes the HMAC check). HMAC and lineage are both necessary and non-interchangeable.
- Taint propagates across mediated inter-agent messages (blocked in agent B's context); an unmediated side channel (agent paraphrasing into free text) is outside scope — the boundary is stated plainly.
- Relaying: honest relays of 1/3/5/10 hops verify and block; rewriting the payload, forging a Trusted label, or stripping the HMAC are all blocked (HMAC mismatch).
- Decode-set D: correct D blocks the attack and allows legitimate calls; a missing decoder (unregistered audio/document extractor) leaks — the failure is an unregistered decoder, not a defeat of the mechanism; an over-broad D falsely blocks legitimate calls -> recommend a small audited allow-list at tool registration.
- Utility: without promotion, 2/3 (67%) of legitimate tasks complete with 1 false block (an OCR'd invoice number legitimately driving a payment); an audited trusted promotion (re-labeling that specific value Trusted, logged) reaches 3/3 (100%) with 0 false blocks while attacks from the same decode origin stay blocked.
- Overhead: MintBinding ~8.3 us + EnforceCritical ~8.7 us = ~17 us per critical call; a decode round-trip is ~11 ms -> +0.16%; the full enforcement path scales linearly with dependency-closure depth (~10 us at depth 1 -> 0.68 ms at 100 -> 6.6 ms at 1000), is flat (~6 us) in the number of tainted contexts, and stays under 0.1 ms for realistic depths (tens).

## Actionable Insights
1. Contain instead of detect: for every "decoding" tool in your agent pipeline (OCR, metadata readers, web scrapers, file parsers, image analyzers), treat its output as untrusted by default and block it from critical actions (sending email, exporting data, payments, file writes) unless it passes an audited promotion path. Example: an agent reading an invoice image -> OCR -> auto-fills an account number -> pays: require an explicit logged promotion (human approval) for any value originating from OCR.
2. Let infrastructure write the ledger; never read agent-presented labels: a compromised agent can attach a fake "Trusted" label, so the verifier maintains the dependency lineage itself and decides on its own record. Example: add middleware logging every tool call with a source ID; the final checker reads the lineage log rather than the agent's claim that "it was verified".
3. Keep D and C as short audited allow-lists at registration: a missing decoder leaks, an over-broad one false-blocks (67% completion). Example: whenever onboarding a new agent tool, mark D (parsing/decoding tools) and C (side-effecting tools) at the registration point and review periodically instead of classifying at runtime.

## Assumptions & Limitations
- Conditions: signing key confined to the MCP layer; all concealment-reversing tools registered in D; the layer mediates every critical call and inter-agent message (fully mediated context).
- Acknowledged: controlled testbed (24 payloads, 3 carriers, 8 evasions, one cover logo, one small local model, keyword/regex/IFC baselines — not production-scale, no learned detector baseline, no production email workflow); proof sketch not machine-checked; scope limit: in-model paraphrase leaving the mediated channel is not captured (future work: taint outputs whose input context was tainted); the defense protects actions, not summary prose (a blocked instruction can still skew the returned summary — residual unquantified); granularity is message/tool-result, not token-level; distributed enforcement requires a shared key or public-key signatures (simplicity traded for scalability).
- Not stated but visible: PSNR/SSIM bound pixel distortion but do not prove perceptual invisibility (the paper says so itself); the 0.5B model is tiny — the security decision is deterministic so model-independence is claimed, but realism with production models is untested.
