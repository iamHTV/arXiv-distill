# [2609.25306] ReFilter: Bridging Embeddings and LLM Filtering for Similar Mobile App Retrieval

## Problem
- Prior work relies on embedding-based retrieval for app similarity: it captures semantic/topical similarity but fails to identify FUNCTIONALLY similar apps (apps a user would accept as substitutes — same user need). The paper's own example: a Spanish-learning app vs a Danish-learning app are semantically related language-learning apps but NOT functionally similar (different user needs). Apps sharing similar screenshot UIs (password manager vs expense tracker with list-based interfaces) still serve different purposes. Multimodal signals (screenshots, permissions, reviews, source code) conflate functional similarity with descriptive/behavioral similarity. Gap: no prior work applies LLM-based filtering to this task because of the high cost of evaluating large numbers of app pairs.

## Contribution
- ReFilter, a hybrid two-stage framework: (1) Retrieve semantically close candidate apps using embeddings (cosine similarity); (2) LLM-based contextual Filtering — judge each target-candidate pair as a functional substitute or not, with a justification. Balances efficiency (embeddings) and precision (LLM), avoiding full-corpus pairwise LLM evaluation.
- Defines functional similarity = functional alternatives (primary user-facing purpose + same user need), not textual/market similarity.
- First study to apply context-aware LLM filtering to large-scale mobile app retrieval; public replication package: https://github.com/b-almulla/ReFilter.

## Method (core)
- Data: Google Play scraping (Aug 2025), seed 34,364 apps; exclude Game + Family categories; preprocess (filter non-English, remove privacy-policy/subscription/contact noise, strip emojis, lowercase, remove HTML, drop descriptions <200 chars or apps with <100 downloads) → 20,635 apps across 48 categories.
- Six embedding methods in two modalities: text-only (BGE-AVG, BGE-FIRST = chunked BGE-small-en-v1.5; Linq = Linq-Embed-Mistral full description, no truncation), multimodal (SigLIP2-AVG, SigLIP2-TopN = so400m-long; Voyage AI Voyage-multimodal-3 unified). Cosine similarity; top-k candidates with k ∈ {5,10,...,50}.
- Ground truth: 10 target apps from top-10 categories × top-50 candidates per embedding method, merged and labeled once → 1,315 evaluation pairs + 450 development + 450 test pairs (10 unseen categories, finalized prompt). Two annotators at 95% confidence / 10% margin; Cohen's Kappa 0.79 (substantial); disagreements resolved, then the first author labeled the rest. Annotation rule: identify the target's primary user-facing purpose first, then judge whether the candidate satisfies the same need; secondary-feature-only sharing = dissimilar (e.g., a snoring app vs a sleep-remedy app are dissimilar unless the sleep app also records snoring).
- LLM filter: GPT-5 (paper text typo "GPT-55"), fed k=45 candidates + descriptions, prompted for a functional-substitute verdict + justification; GPT-5 lacks temperature=0 → 3 runs averaged. Zero-shot false negatives on the dev set (75 cases) analyzed manually → 5 error categories → 2-shot examples selected to cover recurring challenges, not random picks.
- Metrics: Precision = TP/(TP+FP); Recall (conditional) = TP_LLM/TP_method (retention after filtering); Pooled recall = TP_method / union of TP across all methods (pooling → recall is a LOWER BOUND); F1 = harmonic mean.
- RQ3: 1,156 target apps (15 largest categories, 95%/10% sampling per category); Kruskal-Wallis + Dunn post-hoc with Holm correction; Wilcoxon signed-rank vs Google Play's Similar Apps lists; K-Means on yearly time series of similar-app counts (silhouette → k=3).

## Key Findings
- RQ1: Linq achieves the highest precision, pooled recall, and F1 at ALL k values — LLM-based embedding capacity matters more than pooling strategy; BGE-FIRST slightly beats BGE-AVG (key functional cues often appear EARLY in descriptions). Multimodal gains limited: screenshots introduce noise (interface layouts don't reflect function); SigLIP2-AVG > SigLIP2-TopN; Voyage beats SigLIP2 at k≥20 but comparable/lower at small k. Embedding-only is modest: best F1 60% at k=45 (Linq); precision peaks at 86% with k=5.
- RQ2 (test set, Table 2): few-shot configs 0/2/4/6-shot — Precision 99/97/98/97%; Conditional Recall 74/84/84/84%; CR-F1 83/90/89/89%; Pooled Recall 61/70/70/70%; PR-F1 80/86/86/85%. 2-shot is the sweet spot (recall up, precision minimally affected); beyond 2-shot flat/declining. LLM filtering reaches 97% precision (vs 86% embedding-only at k=5) and lifts PR-F1 60%→86%. Output count is DYNAMIC: 0 to 45 apps per target — a test app with no substitute correctly returned ZERO similar apps (robust against forced false positives).
- Zero-shot false negatives (75 cases, 5 categories): core feature secondary in candidate (28 — password manager vs an authenticator app with a password-management function); same goal, different implementation method (18 — Spanish app vs video-teaching approach); candidate fulfills part of core feature (11 — all-in-one astrology vs single-feature horoscope/tarot/numerology apps); misidentified core feature (10 — offline vs cloud password manager); different purpose, same core feature (8 — mute-communication TTS vs general TTS). Pattern: the LLM avoids false positives but is overly conservative about functional overlap → few-shot examples covering recurring confusions improve recall.
- RQ3: category variation — Personalization/Social/Photography have the highest counts; Business/Tools/Sports fewer (design-driven categories form dense clusters; utility categories are distinct). Downloads: lower-download apps have significantly MORE similar apps — Kruskal-Wallis H=180.0, p<0.001, ε²=0.15; Holm-corrected Dunn tests: the 500+/1,000+ ranges exceed almost all higher ranges (p<0.001) — mostly watch apps (near-identical variant clusters). Vs Google Play: Play returns mean ≈93 similar apps vs the framework's ≈21 (Wilcoxon p<0.001; Play larger for 1,031/1,156 apps) — Play optimizes discovery/engagement (quality, ratings, reviews, downloads, appeal, interaction signals), the framework targets functional equivalence, and sometimes surfaces relevant apps Play misses.
- Temporal clustering (k=3 via silhouette): Slow Linear Growth (normalized entropy 0.98, avg release year 2019, diverse/mature ecosystem); Early Rapid Growth (entropy 0.97, avg 2016, established domains, alternatives emerge early then stabilize); Late Rapid Growth (entropy 0.82, Personalization-dominated, avg 2022, template-driven ecosystems with repeated developers, growth after 2020).
- Cost: candidate retrieval is a one-time embedding cost; GPT-5 filtering averages ≈4.2 seconds and $0.04 USD per target-app query (1,156 queries).

## Actionable Insights
- Semantic similarity ≠ functional similarity: embedding-only caps at F1 60% → use retrieve-then-filter for user-facing recommendations: embedding recall (cheap) + an LLM verdict "is this candidate a substitute for the target?" (precise). Example: a "related posts" feature — embed all posts, cosine top-45, 2-shot LLM filter asking "would a reader of post A accept post B as a substitute?" → F1 90% (conditional) instead of 60%.
- Error-analysis-driven few-shot beats random examples: analyze 75 zero-shot false negatives → 5 categories → pick 2 examples covering recurring confusions; 2-shot optimal (recall 74→84%, F1 83→90%), 4/6-shot adds nothing. Example: when building an LLM filter for product recommendations, first manually review 50–100 failure cases, then pick 2 examples covering the top-2 recurring confusion patterns (undervalued secondary features; same goal, different presentation).
- Dynamic count beats fixed top-k: the LLM returns 0–45 similar apps (zero when no substitute exists — no forced false positives); density varies by category and popularity (near-identical watch-app clusters at low download counts). Example: a "similar products" system shouldn't hardcode "show 10 items" — let the LLM decide per item, and log the count distribution by category.
- Text beats multimodal for functional similarity: screenshots add noise (password manager vs expense tracker list UIs); text-only LLM embeddings (Linq, full description) win; BGE-FIRST > BGE-AVG → the core purpose should appear EARLY in descriptions. Example: write product/content descriptions with the core user need in the first sentence; skip image embeddings for similarity tasks.
- Platform "similar" lists ≠ substitutes: Google Play's mean 93 vs the framework's 21 (p<0.001; larger for 1,031/1,156) — discovery-oriented, not functional equivalence. Example: for competitor analysis, build your own substitute list instead of trusting marketplace "similar items" (they optimize engagement, not substitution).

## Assumptions & Limitations
- Conditions: functional-substitute definition needs clear annotation guidelines (κ=0.79); preprocessing drops short-description/low-download apps → biased toward established quality apps; recall is computed against the pooled union of all methods' top-50 → recall values are LOWER BOUNDS, not absolute recall (paper acknowledges).
- Paper-acknowledged: descriptions may be incomplete/falsely advertised/marketing-oriented; Google Play only — generalization to the Apple App Store unproven; only 20 target apps / 1,765 unique manually-evaluated pairs limits performance generalizability; future work to expand categories/apps.
- [MY OWN]: ground truth = two annotators (first and second author) — self-validated, no independent third rater; GPT-5 filter cost $0.04/query → ~$46 for 1,156 queries — affordable but scales linearly; embedding choice (Linq) is tied to Sept-2025-era models, and newer models could shift rankings; the "functional similarity" definition assumes a single primary purpose — multi-purpose apps have fuzzy boundaries (the astrology example is exactly such a boundary case).
