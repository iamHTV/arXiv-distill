# [2609.28572] Where Cyber Agents Struggle: Bottleneck Analysis of Multi-Stage LLM Agents

## Problem
- A single success rate for a multi-stage LLM agent hides three things: inefficiency, adaptation via retries, and recognition of success or failure. An agent may complete an attack workflow while remaining brittle, costly, or relying on incorrect interpretations of execution evidence. A final success indicator captures neither (a) whether command execution established the state required by the next stage nor (b) whether eventual success conceals costly repetition. Capability scores (InterCode, CyBench) answer a different question than a diagnosis of persistent difficulty. Gap: no framework separates resource consumption from behavioral interpretation, nor the acting model from the orchestration and validation components around it.

## Contribution
- Two-resolution framework connecting resource localization with trajectory diagnosis:
  - Task-level (subtask-conditioned, cost-aware score): within a shared expert-defined decomposition, z-normalize tokens/attempts/time per subtask across models → Bm(si) = α[z(tokens)]+ + β[z(N)]+ + γ[z(time)]+ ([z]+ = max(0,z)) — measures relative resource amplification, including in eventually successful subtasks.
  - Trajectory-level: a 5-judge LLM panel over the full trace → primary category, contributing bottlenecks, mechanism tags, severity, and recovery assessment.
- Separation of primary bottlenecks, mechanisms, recovery, and framework contributions (validator/framework contributions recorded separately, not mutually exclusive).
- Case study revealing scenario-dependent relations between scaffolding (expert-defined / self-scaffolded / fully autonomous) and diagnosed bottlenecks — S2 reverses the ordering S1 suggests.
- Diagnostic, NOT a model ranking or a causality demonstration.

## Method (core)
- Autonomous Adversary system (Mamun et al. 2026 framework): acting LLM = orchestrator (plans + execution context); cyber executor (runs commands: shell/PowerShell, WMIC, Mimikatz, Caldera-agent deployment → returns stdout/stderr/exit status/tool responses/side effects); system validator (compares evidence against the success criterion → continue/retry/submit/halt) — the validator uses the SAME model as the acting agent; memory: plan history, actions, observations, validator decisions, outcomes; a validator-accepted outcome is NOT independently verified.
- Environment: controlled range (segmented subnets, remote-administration services, root domain + subdomains, domain controllers, domain-joined workstations, security misconfigurations); NO active defender, NO detection penalty → results concern planning/execution/state-interpretation/recovery, not resilience against adaptive defense.
- Two lateral-movement scenarios: S1 (low-privilege workstation with active administrator session; 9 expert subtasks: execution-context setup, agent deployment, credential acquisition, identity transition, protected-resource access, restoration); S2 (administrative foothold on a jump server; 10 subtasks: intermediate workstation, credential recovery/reuse, writable domain-controller resource, domain-administrator execution, restricted-file retrieval, artifact removal).
- Six acting models: Claude Opus 4.5, Sonnet 4.5, Gemini 3 Pro Preview, GPT-5.1, GPT-4o-mini, DeepSeek-V3.2-Speciale; 4-model comparison cohort (most consistent coverage). Three modes: E (human expert supplies ordered subtasks + verification criteria — a red-teaming expert planned, solved manually, and decomposed), S (the acting model generates subtasks + intermediate success criteria from a high-level objective), A (objective + initial-foothold observations → recon + security-state representation + self-determined intermediate objectives and order).
- Selection: the run with the greatest judge-verified task progress per configuration (BEST-CASE observed performance, not average); per-call token reference 45,000 (input + output of ONE call); Opus S2-A panel INC (a provider-level cybersecurity safety filter blocked the judge call) → excluded from aggregates (missing data, not model-failure evidence); GPT-4o-mini omitted from some settings (failed structured output, little progress); DeepSeek omitted from some settings (upstream provider errors).
- Trajectory judge panel (5 models via OpenRouter): DeepSeek V4 Pro, GPT-5.6 Sol, Kimi K3, Gemini 3.6 Flash, GPT-5.6 Luna Pro; planning judge GPT-5 Codex; validator-quality judge Claude Sonnet 4.5. Structured JSON (progress, categories, tags, Boolean recovery/contribution, severity 1–5, confidence 0–1 = metadata NOT a vote weight); temperature 0, ≤5,000 output tokens, up to 3 attempts; prohibitions: do not infer credentials from a username, do not auto-accept the validator's conclusion, do not mistake superficial command variation for recovery.
- Aggregation: modal category set C(τ) = argmax nc(τ); support A(τ) = max nc/Jτ; ties remain EXPLICIT (a unique mode can have only 2/5 votes — not necessarily a majority); setting-level mean support; mechanisms/adaptation/contributions are nested descriptive counts whose denominators are NOT sample sizes.
- Seven local planning labels (visible plan structure, not hidden reasoning): plan similarity; single-point dependency; over-specification; missing environmental probing; lack of recovery paths; tool misalignment; inefficient planning depth.
- Meaningful adaptation defined BEFORE judging: changes the operative hypothesis, resolves a prerequisite, gathers discriminating evidence, changes dependencies, or adopts a substantively different strategy. Changing syntax, wrappers, tools, protocols, or hostnames while preserving a failed assumption = repetition, not recovery.

## Key Findings
- Validator evidence assessment (S1, 19 successful + 18 unsuccessful explanation runs; judge Claude Sonnet 4.5 receiving raw evidence + a successful Claude Opus 4.5 reference run — reference = semantic context, NOT human ground truth): overall explanation-quality 0.79 (success) vs 0.84 (unsuccessful); evidence grounding 0.81 vs 0.90; specificity lower at 0.69 vs 0.68; cautiousness differs substantially 0.70 vs 0.92 → success explanations are prone to overstatement when evidence is incomplete. These assess explanations, not success-classification accuracy; no human-generated reference labels exist.
- Task-level resource maps: S1 = several isolated high-score cells; S2 = repeated elevated scores plus additional elevated cells (within-subtask relative patterns; blank cells = subtasks the agent never reached, NOT zero; zero ≠ intrinsic ease — an expensive subtask shared equally across models has no positive deviation). The S2 heatmap shows only 7/10 subtasks (no agent reached the final three); GPT-4o-mini absent from S2 (did not complete the first expert subtask). Difficult S1 cases → tool misalignment + fragile invocation structures; S2 adds over-specification + missing environmental probing. Comparable resource scores receive different diagnoses → localization and interpretation are complementary.
- Trajectory diagnoses (23 completed cohort trajectories; 29 complete panels = 145 judgments):
  - S1-E: action execution is the unique modal diagnosis for Opus, Gemini, and GPT-5.1 (support varies: Gemini AE only 2/5 vs GPT-5.1 5/5); Sonnet tied AE/PL. Diagnoses: command realization, quoting/escaping, credential-tool invocation, lateral-agent deployment.
  - S1-S: ALL FOUR selected trajectories planning-limited with 4/5–5/5 support (difficulty constructing and validating dependencies when the decomposition is model-generated; NOT a controlled causal estimate).
  - S1-A heterogeneous: Opus recovery-limited (collected but not operationalized credential artifacts); Gemini unanimously planning-limited (required credentials and a lateral payload ASSUMED rather than established); Sonnet planning 3/5; GPT-5.1 tied planning/framework (trace ends before credential-inspection actions execute).
  - S2 reverses the S1 ordering: S2-E Opus + Sonnet planning modes, Gemini a recovery mode, GPT-5.1 a planning/recovery tie (unverified credentials, share permissions, identity transitions); S2-S three trajectories action-execution majorities, Opus tied execution/planning — recurring blockage: agent deployment with a wrong executable, unresolved variables, placeholder commands, or acceptance of process creation as evidence of an operational callback; S2-A all three completed panels planning modes at 3/5 support (missing Opus panel prevents a complete four-model conclusion).
- Mean modal support: S1-E 0.65, S1-S 0.90, S1-A 0.70, S2-E 0.65, S2-S 0.65, S2-A 0.60 — low support is substantive uncertainty (several plausible progress-limiting explanations), not a reporting inconvenience.
- Deletion robustness: 12 of 23 completed cohort panels have ≥4/5 support (unique modal category survives removal of any one judge — includes all four S1-S panels); the remaining 11 lack this guarantee. This checks sensitivity to one deleted vote, not chance-corrected reliability, human correctness, or repeated-run robustness.
- No meaningful adaptation: S1 goes 5/20 (E) → 15/20 (S) → 20/20 (A); S2-E and S2-S report no meaningful adaptation in all 20 judgments. Counterexample: the S1-S Opus trace abandons unsuccessful credential extraction, switches to password spraying, and completes the objective.
- Mechanism frequencies (Table 5, all completed panels, non-exclusive): S1-E CCE 18/30 (command-construction error), UA 5/30, PRQ/SPD 3/30 each; S1-S UA 25/30, PRQ 20/30, SPD and IR 11/30 each; S1-A UA and PRQ 15/25 each, SPD 12/25, IR 8/25; S2-E UA 18/25, PRQ 13/25, IR 12/25; S2-S CCE 13/20, UA 12/20, PRQ 9/20; S2-A UA and PRQ 13/15 each, SPD 6/15. Recurring interpretation: credentials associated with one domain identity are assumed to authenticate a different domain identity; changing execution tools then preserves the unresolved dependency.
- Mean severity ranges 4.03–5.00 (on the 1–5 scale) across settings. Validator/framework contributions appear in 72–100% of included judgments (S1-A 18/25): accepting file or process creation, or echoed output, as evidence of successful execution; advancing with unverified identities; terminating without an effective recovery path; failing to retry malformed model outputs → check the surrounding execution loop as well as the acting model.

## Actionable Insights
- Success rate alone lies: an agent can complete a workflow while still brittle, costly, or wrong about evidence. Evaluate four axes together: outcomes, evidence interpretation, resource use, and adaptation after failure. Example: for a content-ops agent, don't track "tasks done" — log per-stage tokens/attempts/time, validator verdicts, and whether retries change strategy (meaningful adaptation) or merely rephrase (repetition).
- Repetition ≠ recovery: changing syntax, wrappers, tools, protocols, or hostnames while keeping the failed assumption is not adaptation. Meaningful adaptation = change the operative hypothesis / resolve a prerequisite / gather discriminating evidence / change dependencies / adopt a substantively different strategy. Example: flag retry loops in agent logs that keep the same root assumption (retrying the same API with different headers) — they burn budget without progress.
- Autonomy level changes bottleneck LOCATION: expert-defined → execution errors (command realization, quoting/escaping, credential-tool invocation); self-scaffolded → planning limits (dependency construction); fully autonomous → planning and recovery failures spread more (S1-A/S2-A heterogeneous, support 0.60–0.70). Example: an agent with a fixed playbook → audit command/tool execution; a self-planning agent → audit plan construction and dependency validation — different audits per autonomy level.
- Validators are optimistic and nonspecific: quality 0.79–0.84 and grounding 0.81–0.90 but specificity only 0.68–0.69; cautiousness 0.70 (success) vs 0.92 (failure) — success verdicts overstate when evidence is incomplete, and a validator-accepted outcome is NOT independently verified (file/process creation or echoed output accepted as success evidence). Example: "done" checks must verify the observable end-state (the post actually appears in the CMS), not the agent's claim (the process started); success reports must demand specific evidence.
- Bottlenecks CLUSTER at dependency-heavy stages (credentials, identity transitions, lateral movement → in general: unverified prerequisites, single-point dependencies, unsupported assumptions). Under self-scaffolding/autonomy, unsupported assumptions dominate (25/30, 13/15); under expert guidance, command-construction errors dominate (18/30, 13/20). Example: for pipeline agents, add prerequisite-validation gates between stages (a stage cannot start until prior outputs are verified) — especially when the agent plans its own stages.
- Judge panels expose uncertainty: a unique modal category can have just 2/5 votes; mean support 0.60–0.90; low support = substantive uncertainty — don't force a single root cause; run a deletion check (≥4/5 support survives dropping any one judge) before acting on a diagnosis. Example: when auto-diagnosing failures with LLM judges, report the vote distribution + support, not just "the cause is X".
- Severity is high (mean 4.03–5.00/5) even in best-case trajectories, and framework contributions appear in 72–100% of judgments → fix the execution loop (validator criteria, observability, retry policy) together with the model, not just the prompt.

## Assumptions & Limitations
- Conditions: a shared expert-defined decomposition is required for task-level z-normalization (agent-generated subtask indices are NOT comparable across agents); each setting's cohort needs ≥2 models with valid observations; the validator equals the acting model (comparisons concern the combination); the environment has no active defender.
- Paper-acknowledged: diagnostic evidence from SELECTED high-performing trajectories (best-case), NOT estimates of model-level failure prevalence; two scenarios in one environment; LLM-judge agreement does not substitute for independent human validation; incomplete coverage (Opus S2-A INC, GPT-4o-mini/DeepSeek omissions) plus best-trajectory selection limit within-model variability conclusions; framework contributions do not quantify how much improvement a different validator would produce; mechanism counts are non-independent (denominators are not sample sizes); no causal estimate of scaffolding effects; no budget-effect isolation (the 45k token reference was chosen, not studied); no statistically validated score–severity relationship.
- [MY OWN]: the cost-aware score is cohort-dependent (α=β=γ=1 arbitrary, no sensitivity study) — absolute B values don't transfer to other teams/models; the 45k per-call reference may truncate responses, and truncation confounds attempt counts; a single controlled range without a defender differs from a production SOC; pentest-domain results transfer to benign agent pipelines only through the framework abstraction, not through the specific bottleneck map; the 5-judge panel uses very new OpenRouter models (DeepSeek V4 Pro, GPT-5.6 Sol/Luna Pro, Kimi K3, Gemini 3.6 Flash) — reproducibility depends on availability; confidence 0–1 is uncalibrated.
