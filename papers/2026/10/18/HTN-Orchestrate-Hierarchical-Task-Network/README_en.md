# 2610.22195v1 HTN-Orchestrate: A Hierarchical Task Network Framework for Multi-Agent Orchestration

## Problem
- Orchestrating multiple agents on a complex task requires reconciling local subtask execution with global task planning. Two families of existing approaches each sacrifice one side: (1) structured workflows (AutoGen, MetaGPT, AFlow — manual or automatically generated) impose clear global structure but FIX the decomposition before execution begins, so findings from local execution cannot reshape subsequent planning; (2) runtime delegation (Magentic-One, AOrchestra, Agent Team by Apodex/Kimi K2.5) lets a central orchestrator determine subtasks and assign agents as execution proceeds, but COUPLES task decomposition, subtask dispatch, and result synthesis within a SINGLE orchestrator, without explicitly modeling subtask hierarchies or precedence dependencies among sibling subtasks. Dynamic decomposition methods (ADaPT, ReAcTree) allow the plan to evolve but provide limited support for representing complex dependencies. The gap: the tension between adaptive local execution and structured global planning remains unresolved.

## Contribution
- HTN-Orchestrate: a two-layer orchestration framework that decouples global task planning from local subtask execution through a hierarchical task network (HTN) that explicitly represents subtask hierarchies and precedence dependencies. Upper layer: the Planner incrementally expands the task network as prerequisite results become available. Lower layer: each executable leaf subtask is delegated to an Orchestrator that coordinates multiple workers.
- Three mechanisms combined: (1) result-informed planning — deferring decomposition decisions for dependent subtasks until prerequisite findings are available; (2) AND-semantic synthesis — results propagate upward through the task hierarchy (a leaf returns its Orchestrator's result; a non-leaf synthesizes only after ALL children complete); (3) a rebuilding mechanism — retaining supported evidence from completed work to construct a revised task network when the current decomposition cannot resolve the task. It is the ONLY system with all five features (STR+RES+DEC+RPL+EVC) vs Agent Team (STR+RES), Workforce (STR+RES+DEC), ADaPT (RES+RPL), FlowSearch (STR+RES+RPL), ChatHTN (STR+RPL).
- Evaluation on five benchmarks (web research, scientific reasoning, research workflows): outperforms ReAct, Agent Team, and DeepSeek Harness with the same backbone model — BrowseComp 89.73% (+2.45pp vs Agent Team, +15.80pp vs ReAct), SUPERChem 73.44% (+4.69pp, +8.21pp), FSR 43.33% (+3.33pp), FSO 79.00% (+4.00pp), PRL-Bench 46.00 (+10.19pp — the largest gain).

## Method
- Task network T = (V, Eh, Ed): hierarchy edges Eh form a rooted tree (each parent is decomposed into children that jointly address its task); dependency edges Ed impose acyclic precedence constraints AMONG SIBLINGS (an edge (u, v) means v requires the result of u). Unlike classical HTN planners (a predefined library of decomposition rules), the Planner uses an LLM to generate decompositions during execution, so the network grows incrementally.
- Ready(v) ⇔ Ch(v) = ∅ ∧ v is pending ∧ every u ∈ Pred(v) is completed. The completed status covers both resolved and open outcomes — downstream proceeds with whatever evidence its prerequisite produced (the resolved-or-open distinction only feeds synthesis and replanning decisions).
- Planner (Algorithm 1): loop over epochs; each epoch: InitializeRoot(q, M) with M = evidence summary; PlanOrExecute each ready planning leaf (consider the original goal, task description, ancestors, and summaries of relevant prerequisite results → either mark for direct execution OR expand with children and sibling dependencies; validate coverage of the parent task and acyclicity of proposed edges, revise if either check fails; depth and branching limits); dispatch ready executable leaves to their Orchestrators in parallel (a wave); PropagateResults (record leaf results, recursively synthesize each parent whose children have all returned); settle the wave or stop it for replanning; if the root is resolved → return the synthesis; otherwise e+1, CollectEvidence extracts supported findings from completed AND partial reports into M (conditioning the new network as planning context, NOT auto-marking subtasks complete); bounded by rebuild limit B and execution budgets → when exhausted, synthesize the evidence obtained so far and report unresolved requirements (the output reflects the sufficiency of evidence rather than treating the stopping condition as success).
- Orchestrator (Algorithm 2): each leaf receives a stable context C_v (the original task, the leaf's objective, relevant ancestor descriptions, and prerequisite result summaries); maintains returned worker reports R_v and active assignments A_v; a decision loop chooses dispatch / wait / finish. Dispatch: select worker roles and generate task-specific instructions based on current evidence — an initial investigation can be followed by a focused search or a verification step when a report reveals a gap or a disputed claim. Progressive collection: follow-up work is scheduled while other assignments remain active. Limits on concurrency, dispatch rounds, and execution time bound the work. Finish: stop work no longer needed, SynthesizeLeaf (summary, resolved/unresolved outcome, evidence references). The outcome reflects the sufficiency of the evidence, not merely whether workers stopped or a verifier was invoked.
- Setup: backbone DeepSeek-V4.1-Flash (high reasoning effort for the orchestration agents, LOW for workers). Workers have two complementary roles: research and verification. Tools: web search, webpage retrieval, scholarly search, Python execution, file reading, report submission (search and retrieval disabled for FSR, FSO, SUPERChem, PRL-Bench). Config: maximum task-network depth 2 (root at depth 0), at most 4 children per node, up to 3 concurrent workers, up to 12 orchestration rounds per epoch, and the Planner can rebuild the task network at most once.
- Benchmarks: BrowseComp (BC — hard-to-find information through persistent web browsing, accuracy), FrontierScience-Research (FSR — open-ended research subproblems, success rate = fraction earning at least 7 of 10 rubric points), FrontierScience-Olympiad (FSO — olympiad physics/chemistry/biology, accuracy), SUPERChem text-only subset of 256 questions (multistep reasoning across chemistry subfields, accuracy), PRL-Bench (theoretical and computational physics research tasks derived from published papers, mean percentage of satisfied rubric criteria on a 0–100 scale). Baselines: ReAct and Agent Team (FrontierAgent), DeepSeek Harness (DSH — Minimal Mode, a single-agent configuration with a persistent shell and file editor, plus web search for BC).

## Key Findings
- Main results: BC 89.73% (ReAct 73.93%, Agent Team 87.28%, DSH 80.33%; only GPT-6 Astra 91.50%, Kimi K3 91.20%, and GPT-5.6 Sol 90.40% score higher — all frontier-scale models). FSR 43.33% (Agent Team 40.00%, Meta Muse Spark 38.00%, GPT-5.5 33.90%, ReAct 25.00% — margins of +18.33pp over ReAct and +3.33pp over Agent Team). PRL-Bench 46.00 (Gemini 3.1 Pro 44.27, +1.73; Agent Team 35.81, +10.19 — the largest gain on any benchmark; DSH 39.89). FSO 79.00% (matching Gemini 3.1 Pro; Agent Team 75.00% +4.00pp, DSH 76.00% +3.00pp). SUPERChem 73.44% (GPT-5.6 Sol 73.60% — only 0.16pp behind the overall best; Agent Team 68.75% +4.69pp, ReAct 65.23% +8.21pp). Gains over Agent Team range from 2.45pp (BC) to 10.19pp (PRL-Bench), largest on tasks that reward structured decomposition and iterative refinement.
- DSH (a single-agent runtime) beats Agent Team on PRL-Bench (39.89 vs 35.81) and matches it on FSO (76.00 vs 75.00) — a focused single agent is competitive on benchmarks rewarding sustained reasoning; HTN-Orchestrate beats both approaches on all five benchmarks while using an open-weight model.
- Execution analysis (200-question BC subset): among 165 shared successes with Agent Team, HTN-Orchestrate finishes faster on 112 (67.9%), with a median per-question completion-time ratio of 0.699. Against ReAct: HTN takes longer on shared successes but answers 38 questions ReAct misses and misses only 12 that ReAct answers (net +26 correct). Average worker concurrency is 2.47 vs 1.70 for Agent Team (2.42 vs 1.82 on shared successes); HTN-Orchestrate spends 24.6% of each run with at least four active workers vs 11.8% for Agent Team, but also a larger fraction of time with no active workers (planning, coordination, or synthesis can still proceed).
- Internal statistics (correct n = 184 vs incorrect n = 16): final tree depth 1.23 vs 1.19 and leaves 3.95 vs 4.00 (similar), but executed leaf instances 4.52 vs 6.31, worker invocations 21.04 vs 47.50, Orchestrator decision rounds 20.21 vs 44.62, and rebuilds 14.7% vs 50.0% — similar final task structures correspond to substantially different execution histories.
- Dynamic decomposition and recovery: the Planner produces child subtasks at nodes with prerequisite dependencies 79 times across 57 of 200 questions (result-informed planning occurs regularly); task-network rebuilding occurs on 35 questions, of which 27 are ultimately scored correct.
- Ablations (200-question BC subset): HTN-Orchestrate 92.0%; Upfront decomposition 90.5% (−1.5pp) — worker invocations 14→16, Orchestrator rounds 14→17, rebuild rate 17.5%→22.5%, median completion 25.23→30.02 minutes (the full system achieves higher accuracy with LESS coordination and lower latency); Single-agent leaf execution 89.5% (−2.5pp) — executed leaf instances 4.67→6.15, rebuild rate 17.5%→32.0% (less effective research within leaves shifts burden to the Planner, which spawns more subtasks and rebuilds more); No rebuilding 89.5% (−2.5pp) — executed leaf instances 4.67→4.12, worker invocations 23.16→19.01 (the higher accuracy comes at the cost of additional research that the rebuilding mechanism makes possible).
- Case studies: Q193 (trace an author of a 1993 RPG supplement through a 2015 children's book and his father's radio program to a station's first broadcast year): the result-informed plan narrows the downstream search to the returned author list and executes four leaves rather than five. Q501 (the third song in a 24-song blog list dated Dec 27, using a weekly-feature clue and the 21st song's album): the initial search fails → the Planner retains candidate albums, recurring weekday features, and rejected posts → rebuilds with a feature-based search and an explicit album-to-list matching task → "Serial Killer" by Tobin Sprout (No rebuilding returns "Silent Night" — wrong).

## Actionable Insights
- Two layers, Planner and Orchestrator: the Planner keeps the hierarchy and dependencies and DEFERS decomposition of dependent subtasks until prerequisite results return; each leaf gets its own Orchestrator coordinating workers. Example: a research agent — don't pre-plan the whole tree; expand "analyze X" only after "find X" returns (narrow downstream search to actual findings).
- Rebuild with evidence carryover, not restart: when a plan fails, extract supported findings from completed AND partial reports into an evidence summary conditioning a new network (without auto-marking tasks complete). Example: web research that cannot find the target post — keep candidate lists and rejected leads, then rebuild with a new search strategy (Q501: correct "Serial Killer" vs wrong "Silent Night").
- Result-informed planning is both more accurate and cheaper: upfront decomposition costs −1.5pp accuracy, +4.79 minutes median, and more worker invocations. Example: decomposing after evidence beats decomposing upfront on the same task — apply this to any multi-step research pipeline.

## Assumptions & Limitations
- Conditions: the method works when the task is decomposable into a hierarchy with sibling dependencies; decompositions are validated for coverage and acyclicity; budgets bound network growth (depth 2, ≤4 children, 1 rebuild); workers need tools suited to the task (web search for BC, disabled for the science benchmarks).
- Limitations acknowledged (future work): scaling the task-network depth for problems requiring deeper decomposition hierarchies; evaluating the framework across additional backbone models (currently only DeepSeek-V4.1-Flash).
- Not stated: all experiments use one backbone model — whether the gains transfer to other models (especially smaller ones) is unknown; the depth-2 cap artificially limits real-world hierarchy complexity; the rebuild limit of 1 leaves multi-cycle recovery untested; the BrowseComp ablation subset (200 questions) has 92.0% accuracy vs 89.73% on the full set (the subset is easier); search tools are disabled on FSR/FSO/SUPERChem/PRL-Bench, so result-informed planning is less material there; no cost/token accounting (worker invocations are counted but not converted to $); no statistical significance tests are reported for the benchmark deltas.
