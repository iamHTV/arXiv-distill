# 2609.31288 — When the Model Retires: An Empirical Study of LLM Migration in Open-Source Applications

## Problem
- Apps built on commercial LLM APIs depend on model versions that providers retire on their own schedule (notice from one year to two weeks). Unlike a library, a retired model cannot be pinned: on the shutdown date every request fails. Model lifecycles have shortened from 18–24 months to 6–12 months. 2026 saw the largest deprecation notice (OpenAI single-day shutdown of GPT-3.5 Turbo/GPT-4/GPT-4 Turbo/o1/o3-mini/o4-mini on 2026-10-23; Assistants API shut down 2026-08-26 after a one-year notice; Anthropic retired every Claude 3.x model between Oct 2025 and Apr 2026 on 60–114-day notices; Google shut down the Gemini 2.0 Flash family on 2026-06-01).
- Prior work documents migration difficulty (a single case study, regression tooling, an end-of-life migration framework, evidence that aggregate scores hide item-level regressions) — but not what happens across the ecosystem when a retirement actually lands: how many applications migrate before the deadline, how many break, and what the migration costs in code.

## Contribution
- Dataset: 22,555 unique commits (17,703 non-fork repositories, 2024–2026; TypeScript 28%, Python 27%, JavaScript 6%) matched to an event table compiled from the three providers' deprecation pages (30 OpenAI, 9 Anthropic, 7 Google entries) → 5,139 matched commits (4,544 repositories), 3,933 concerning already-shut-down events (timing analyses).
- First ecosystem-scale measurement of reactive (post-shutdown) vs proactive migration: 82% (95% CI 79–84) of migrations were committed AFTER the shutdown date — after the application had started failing — reweighted by the human-validated genuine rate (two coders, stratified sample of 300, κ=0.89–0.95; only 62% of matched commits genuine; genuine rate 24–80% pre-shutdown vs 48–86% post → reweight by stratum).
- Dose–response on notice policy: 89% reactive for Anthropic's 60–114-day notices vs 13% for OpenAI's one-year Assistants API notice; logistic regression on log(notice days): coefficient −1.36 (reweighted) — each e-fold increase in notice reduces the odds of post-shutdown migration by ~74–78% (raw −1.52; Google soft-notice assumption −0.95). Event-level Spearman ρ=−0.53 (p=0.06, n=13).
- A keyword-and-manual taxonomy of breakage (4 forms) plus evidence on migration size and architectural adaptation.

## Method
- GitHub commit-search API, 22 query strings (retired model identifiers/endpoint names + migration vocabulary: deprecated, retired, migrate, shutdown, model not found), quarterly windows (2024–mid 2025) + monthly (mid 2025–Sep 2026), 200–300 results per window. Forks excluded, de-duplicated by SHA. GraphQL metadata (stars, forks, archived flag, language) for 22,513 commits; REST file paths + patch hunks for all 3,933 retired-event commits (3,931 retrievable).
- Matching: the most specific model/endpoint pattern with word boundaries (short identifiers like o1 require delimiters on both sides); a migration verb is required (migrate, replace, switch, upgrade, update, remove, drop, swap, retire, deprecate, sunset, shut down); excludes commits more than 30 days before the announcement, AI-tool authorship headers that embed a model identifier, and dependency-bot commits; excludes commits where the retired identifier is the destination of an arrow or the named destination is an older model (migrations INTO the model) — removed 33% of candidates, concentrated in Google events.
- Timing: a migration is reactive if committed after the shutdown date. Dose–response analyses use only events retired ≥28 days before collection and commits within [−365, +180] days of shutdown (right-censoring control).
- Keyword classifiers: breakage (404, not found, fail, broke, error, crash), silent failure, pinned snapshots, abstraction layers (LiteLLM, OpenRouter, LangChain, router, gateway, fallback, provider-agnostic), evaluation, prompt/parameter changes, cost. Keyword rule performance against human labels: breakage precision 0.81/recall 0.92; silent failure 0.57/0.57; abstraction 0.70/0.42; pinned snapshot 0.25/0.83 (pinned-snapshot rates therefore not reported).

## Key Findings
- RQ1: 72% raw post-shutdown; 82% reweighted (CI 79–84). Median migration landed 39 days after shutdown, 158 days after announcement. Among genuine post-shutdown migrations: 40% production repairs, 45% planned changes with no breakage mentioned, 14% catalogue cleanup (soft shutdowns, applications not in active use). Popularity has NO detectable association with timing: raw 72% (0-star), 71% (1–9), 71% (10–99), 74% (100+); reweighted 82/80/81/82 — star count is not a proxy for retirement readiness (holds after excluding catalogue-like projects, 16% of commits). Reactive fixes arrive slowly: 9% within a week, 27% within a month, 55% within three months — a retired model typically leaves an application broken for weeks. Short-notice retirements arrive as waves: the week after the Claude 3.5 Haiku, 3 Haiku, and Opus 4.1 shutdowns each carried 25× the weekly volume of the previous 8 weeks, vs 2.1× for the Assistants API and 1.3× for Gemini 2.0 Flash.
- RQ2: Reweighted reactive share: Anthropic 89% (CI 88–91), OpenAI 66% (59–73), Google 64% (52–78). Event level: 60–76-day Anthropic retirements saw 86–98% reactive migration; the one-year Assistants API notice saw 13%. Regression: −1.52 raw / −1.36 reweighted (SE 0.09, p<0.001) — each e-fold increase in notice reduces the odds of post-shutdown migration by ~74–78%. Gemini 2.0 Flash natural experiment (date moved from 31 March to 1 June 2026): NO discontinuity — migrations trickled in at 23–29 per week from February through July, a modest dip from 28.5 to 23.5 per week in the four weeks after the postponement became known, and no spike in the week after the actual shutdown — a soft, movable date produces neither a deadline effect before shutdown nor a breakage wave after it (the 25-fold spikes of Anthropic's firm 60-day retirements are the contrast). Claude Sonnet 4 (62-day notice, 79% reactive): a short notice on a current-generation model draws somewhat faster reaction, but still leaves four in five applications migrating after the fact.
- RQ3: By keyword, 41% of matched commits describe breakage (48% post-shutdown, 29% pre-shutdown). Among human-validated genuine migrations, breakage appeared in 63% of post-shutdown Anthropic migrations, 29% of Google's, 19% of OpenAI's (pre-shutdown: 42%/33%/4%). Four forms: (1) hard failure — the endpoint returns 404/not found and the feature stops ("every outreach draft 404'd after discovery succeeded"); (2) silent failure (8% of genuine migrations, 14 of 180) — exception handlers converted the retired-model error into an apologetic chat message, a null result, a demo-mode fallback, or—in one case—a constant answer ("breed identification always returned 'Golden Retriever'"); "AI analysis had been failing silently in production" for weeks after the Gemini 2.0 Flash shutdown; (3) parameter incompatibility (7.5% of commits) — the replacement model rejects max tokens or non-default temperature, so a rename alone does not restore service; (4) pinned snapshots — dated identifiers (claude-3-5-sonnet-20241022) named as the proximate cause in 6 of 118 agreed genuine migrations (a keyword rule overstates this by an order of magnitude → present but uncommon).
- RQ4: Median 2 changed files (75th percentile 5), 14 added and 6 deleted lines. 94% of migrations edit source — the model identifier was hard-coded (only 6% touch config/docs alone; reweighted 6.4%; human-validated subset 1.7% config-only → hard-coding is even more prevalent among true migrations). The identifier had to change in a median of one file, but in 26% of migrations in three or more files; 16% touch a test file (12% for prompt-only). Architecture: 78% prompt-only, 13% tool/agent calls, 8% retrieval, 2% fine-tuning. Effort scales: prompt-only 2 files and 6 lines; agent applications 5 files and 63 lines; RAG 7 files and 155 lines; fine-tuned applications 14 files and 693 lines (the replacement base model invalidates the tuned checkpoint). Human-validated: prompt-only 2 files/7 lines; agent, RAG, and fine-tuned 8–9 files and 224–411 lines. Reactive shares are similar across architectures (58–74%) — heavier applications are not more proactive, they merely pay more when the retirement lands.
- Abstraction layers are rare and mostly retrofitted: only 3% of migrations occur in code that already routed calls through an abstraction (LiteLLM, OpenRouter, a gateway, a model map; 3% reweighted, 7% human-validated) — the smallest non-trivial migrations (4 files, 20 lines) but no less reactive (70%). A further 4% introduce such a layer during the migration (the largest non-fine-tuning changes: 6 files, 164 lines). The remaining 93% simply rename the identifier in place. Retirement events trigger architectural hedging for one migration in twenty-five; a pre-existing layer reduces the size of the fix without making it timely.
- RQ5: 20% of commit messages mention an abstraction layer/gateway/fallback, but only 4% actually add one; 8% modify prompts; 13% mention cost; 4.5% mention an evaluation or regression suite; 11% add an assertion or evaluation line in the patch. Retirement events trigger far more renaming than measurement — applications switch the model without a harness that would reveal item-level regressions. 43% of matched commits carry an AI coding-assistant co-author trailer (reported without interpretation).
- RQ6: Of the 3,933 retired-event migrations, 2,236 name a destination model. Only 8% move to a different provider (7% reweighted, 8% human-validated); 68–74% stay with the provider that retired their model (Claude 3.5 Sonnet → Sonnet 4.6 or Haiku 4.5; GPT-4 Turbo Preview → GPT-4o); 16% add a second provider alongside (hedging, not switching). The switch rate is the same whether the migration was reactive (7%) or proactive (13%) and whether breakage was reported (7% either way) — being burned does not drive applications away. No evidence of learning: 85 repositories were hit by two or more retirements, with a post-shutdown share of 73% at the first event and 73% at later ones (bootstrap 95% CI for the difference −13 to +13pp), although later migrations landed sooner (median 22 vs 45 days). Retirement is therefore not a churn event for providers; it is a forced upgrade funnel.

## Actionable Insights
- Externalize the model identifier (env var/registry): 94% of migrations edit source because the identifier is hard-coded — indirection would turn the majority of these migrations into a one-line change. Example: a coding app using a `MODEL_ID` env var + model registry map → a retirement event needs only a one-line config change instead of editing 94% of the codebase.
- Put a static deprecation check in CI: flag model identifiers against the providers' deprecation tables and fail CI BEFORE the shutdown date — this would have prevented most post-shutdown commits in the corpus. Example: a nightly job queries the OpenAI/Anthropic/Google deprecation pages and fails CI if the codebase contains an identifier retiring within 90 days.
- Notice length is the only lever that predicts proactive migration (dose–response: −74–78% odds per e-fold): a 60-day notice → 86–98% reactive; a one-year notice → 13%. Example: with a provider that gives only 60-day notices (Anthropic-style), set the internal migration deadline at announcement + 30 days, not shutdown − 7 days.
- A migration playbook by architecture: prompt-only 2 files/6 lines, agent 5 files/63 lines, RAG 7 files/155 lines, fine-tuned 14 files/693 lines (checkpoint invalidated). Example: before adopting a fine-tuned model, budget the migration effort at ~700 lines plus retraining — the retirement cost exceeds the deployment cost.
- A pre-existing abstraction layer does NOT guarantee timeliness (70% still reactive) — it only shrinks the fix (4 files/20 lines). "We support multiple providers" and "we survived a previous retirement" are NOT evidence of resilience (73%→73%). Example: don't rely on LiteLLM alone — add a retirement watch and periodic migration drills.
- Beware the silent failure mode (8% of migrations): exception handlers convert the retirement error into an apologetic message/null/demo-mode/constant answer — the app "works" but is wrong. Example: monitor the rate of fallback/demo-mode responses, not just the error rate.

## Assumptions & Limitations
- Recall: only migrations whose commit message names the retired identifier are observed; silent migrations and abandoned projects are under-represented (archived <1%; abandonment without archiving is common).
- Precision: 38% of matched commits are non-genuine (two-coder judgement), concentrated pre-shutdown and in Google events → headline shares are reweighted by stratum genuine rates; file-level and destination analyses report both reweighted values and the human-validated subset (agreeing within a few percentage points).
- Search caps: GitHub commit search returns ≤1,000 results per query and the windows retain the first 200–300 → counts are lower bounds and popular months are truncated; re-running 12 random windows: Jaccard 1.0 for the 9 uncapped windows, strict subsets for the 3 capped; Gemini 2.0 Flash (which dominates the Google sample) is the most truncated.
- Right censoring: recently retired events are excluded from dose–response (retired ≥28 days before collection).
- Google is excluded from the notice-length regression (announcement date not archived); a sensitivity analysis under the soft-notice assumption (GA 365-day, preview 14-day) yields a weaker −0.95.
- Pinned-snapshot κ=0.62 (moderate) → reported only as a lower bound; the keyword rule overstates it by an order of magnitude → the pinned-snapshot rate is not reported.
- The 300-commit validation sample is stratified on the outcome → it cannot re-estimate the regression directly.
