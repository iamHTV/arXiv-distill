# Skill: emma-scoped-episodic-memory (scoped episodic memory for multi-agent workflows)
Source: 2610.35966
Type: framework / workflow

## When to use this skill
- Building or operating a multi-agent system for a specialized domain that needs fine-grained procedures a general model lacks — multi-channel content pipelines, data-to-insight pipelines, multi-application tasks.
- You want the system to improve from failures WITHOUT fine-tuning weights and WITHOUT paying experts to re-author the topology for every new domain.
- Do NOT use: simple tasks where one agent suffices (plain episodic context such as a playbook is enough); domains with no automatic correctness signal (LLM judge, unit tests, exact match) to gate attempts; when you need gradient-level rather than text-level inspection.

## Inputs required
- A task set with ground truth or an automatic per-task verifier (gate correctness signal).
- One backbone LLM running controller + sub-agents + reflector (EMMA shares one backbone per run; a strong reflector with weaker executors is a natural pairing the paper suggests as future work).
- A repository/tool environment for sub-agents to execute in (a Python tool per agent).
- Budget: EMMA re-runs only failed tasks — 17–38% fewer executions than the most efficient baseline (61.8 vs 96.8–280.0 mean over five backbones on KramaBench).

## Steps
1. **Initialize the 3-pool memory:** C (controller memory — rules to decompose/dispatch/verify; entries carry topic, summary, domain tags, generality label), A (agent pool — start with one generalist a0 with prompt p0), S (skill pool — short procedures for classes of sub-problems, one-line "when to use" index). Memory persists across tasks, written ONLY during training; frozen at inference, no writes.
2. **Attempt chain per task:** fresh environment; the controller loads selected memory entries (it chooses from the index itself — loading none is valid), emits an ordered plan (each step: agent + subtask + skills), dispatches ONE step at a time; each sub-agent receives the task, its subtask, its skills and a controller-curated summary of earlier outputs. Gate with the task's correctness signal: correct ends the chain; incorrect triggers reflection.
3. **Overflow decomposition (when a step is exhausted):** the sub-agent runs out of context window or rounds → do NOT conclude the agent failed; the subtask was specified too coarsely: the controller uses the partial trace to split the step into smaller steps over existing agents, splices them into the plan, resumes at the same position preserving completed work; record the overflow as reflector evidence.
4. **Structured reflection, fixed 4 steps:** localize the failing step → classify into one of five scopes: execution_slip (knew the method, slipped once), agent_behavior (a general working habit failed), procedure (the method for a class of sub-problems is wrong/missing), missing_capability (no agent in the pool can do this work), routing (subtasks correct but decomposition/dispatch wrong) → generalize the correction to every task of the same kind, naming NO entity or answer of this task → minimize to the smallest change within the scope. Output exactly ONE action per the ownership table: execution_slip → REVISE_PLAN/NO_CHANGE (a plan directive for this task only, never written to durable memory); agent_behavior → REFINE_PROMPT (p0 if general, the specialization prompt if role-specific); procedure → REVISE_SKILL/CREATE_SKILL; missing_capability → CREATE_SKILL then CREATE_AGENT; routing → MEMORY_NOTE/REVISE_PLAN (CREATE_AGENT on overflow).
5. **Guarded update — five programmatic guards, never backbone-dependent:** (a) scope–action compatibility — the action ∈ Act(z); (b) prompt preservation — keep most of the existing prompt, only touch agents that ran in the failed attempt; (c) bounded growth — pools and entries stay within fixed sizes, a new agent must be a genuine specialization, not a duplicate or a label; (d) no leakage — no artifact may contain the reference answer or copy a span of the task text; (e) change of strategy — no memory level edited in more than two consecutive failed revisions; if the same step overflows twice in a row, the action must change how the work is split. Refused proposal → its reason goes back to the reflector, which retries; persistent refusals → no change.
6. **Re-run + exercise + freeze:** a newly created or revised skill/agent is NAMED in the re-run's plan (the edit is actually exercised); re-run until success or the revision budget is spent; NO edit after the final failure (an edit never re-run is untested memory); an end-of-task controller update records a few routing lessons; snapshot memory after each chain; freeze after one pass — no checkpoint selection. At inference the controller keeps selection/replanning/overflow decomposition, but no reflector and no writes.

## Expected output
- A frozen episodic memory artifact (one per benchmark/backbone): controller routing rules + specialist agent prompts (each specialist p̃_j = p_0 ∥ p_j — a general habit written once in p0 reaches every specialist) + the procedural skill pool.
- Verified performance: best mean on every benchmark (KramaBench 0.654 vs 0.584 GEPA (+7.0 points); BBEH-mini 0.663 vs 0.605 (+5.8); AppWorld normal +11.9 TGC/+17.4 SGC, challenge +6.4/+5.3 over ACE); first in 17/20 settings; EMMA's weakest backbone (58.5 KramaBench, 61.2 TGC AppWorld challenge, 56.3 BBEH) stronger than every baseline's weakest backbone; up to +32.5% over the strongest baseline; 17–38% fewer training executions.
- Ablation-verified: skills +8.5 points (0.506→0.591), agents +5.6 (0.591→0.647) on KramaBench with Opus 4.5; test-time adaptation (DACode 0.443, Reflexion 0.476, DeepResearch 0.535, EvoMAS-on-test 0.532) all well below EMMA 0.647.

## Example application
- A 3-channel content factory (blog, email, social): the generalist a0 prompt holds the house style; training on 30 tasks with a verifier (fact-check + format check): failure "blog article missing sources" classifies as procedure → CREATE_SKILL "every numeric claim must carry a source"; failure "social agent posts at wrong time" classifies as routing → MEMORY_NOTE "channel social → dispatch after blog approval"; overflow on a data-analysis task → CREATE_AGENT analyst specialist inheriting p0. After one pass the memory freezes; at inference the three channels run with memory, no reflector.

## Gotchas
- Ill-scoped evolution is the main trap: WITHOUT scope constraints the backbone decides the structure — Opus accumulates skills, DeepSeek repeatedly creates agents (Figure 1). The guards are mandatory, not optional; dropping guard (a) or (e) lets memory drift toward the backbone's habits.
- execution_slip is NEVER written to durable memory (a one-off slip is not a pattern) — counter-intuitive but correct: persisting every failure makes the memory noisy.
- The generalize step is mandatory: a correction naming task-specific entities/answers does not transfer — "a lesson at the wrong level never fires again or contaminates unrelated tasks" (Table 1 caption).
- Generalist prompt inheritance (p̃_j = p_0 ∥ p_j) means an edit to p0 propagates everywhere — good for consistency, but one harmful edit in p0 affects every specialist; prompt preservation only checks agents that ran in the failed attempt, so review p0 edits manually.
- Edits persist even when the chain ends unsolved — the paper acknowledges ineffective or harmful entries may remain (no systematic degradation observed); hygiene: periodically cross-verify memory on mini-batches or replay old tasks (the paper's future work — do it yourself).
- The gate needs a trustworthy automatic verifier: a noisy LLM judge makes reflection learn from false failures; unit tests miss behaviors (as paper #265 warns) → scoped edits fix the wrong layer.
- The controller chooses memory entries itself ("loading none is valid") — a weak controller can ignore useful memory: monitor the load rate of memory entries; entries never loaded are cleanup candidates.
