# 2610.35966 EMMA: Structured Episodic Memory for Multi-Agent Workflow Synthesis

## Problem
- Deploying LLM agents in specialized domains requires fine-grained task-specific procedures and knowledge a general model lacks. The two conventional mechanisms each incur a distinct cost: parameter training (supervised fine-tuning or reinforcement learning under objectives such as GRPO/DAPO) is computationally expensive and yields an artifact that can be neither inspected nor selectively corrected; hand-engineered agent systems avoid that cost but transfer it to expert labor and must be re-authored for every new domain.
- Episodic memory (persisting task-solving experience as text with model weights frozen) updates at the context level, but single-agent adaptation struggles to reduce cross-task interference, especially for complex tasks such as multi-application navigation or data pool analysis. Multi-agent evolution alleviates this, yet prior methods (ACE, GEPA, EvoMAS, ADAS) lack clear definitions of update rules and rely on the backbone model to decide where and how much the system changes — ill-scoped evolution: learning follows the backbone's structural preferences rather than observed failures. Figure 1: without scope constraints, Opus 5 accumulates skills while DeepSeek v3.2 repeatedly creates agents — orthogonal structural preferences that overshadow what is actually learned.
- Gap: no existing system makes the ownership and admissibility of updates explicit — each failure must be assigned to the scope that owns its correction and fixed by exactly one bounded edit within that scope.

## Contribution
- EMMA (structured Episodic Memory for Multi-Agent workflow synthesis): formulates multi-agent workflow synthesis as episodic learning over the system's configuration — controller routing memory, specialists inheriting the generalist prompt, and per-step procedural skills are all memory entries.
- Structured reflection + scoped updates: a reflector assigns each diagnosed failure to one of five scopes and proposes exactly one edit within it; backbone-independent guards keep every accepted edit scoped, incremental and bounded.
- Numbers: best overall performance on EVERY benchmark (KramaBench, AppWorld, BBEH) across five backbones and four baselines; up to 32.5% over the strongest baseline; first in 17 of 20 settings; 17–38% fewer training executions than the most efficient baseline.

## Method (core summary)
- Hierarchical episodic memory, three pools of decreasing generality: C — controller memory (rules for task decomposition, agent/skill dispatch, when to verify; each entry carries a topic, summary, domain tags and a generality label — general/domain-specific/task-specific; the controller reads the index and chooses which entries to load — loading none is valid because irrelevant memory degrades planning); A — agent pool (each sub-agent = system prompt + input/output contract + Python tool; training starts from one generalist a0; specialists created during training inherit the generalist's current prompt, p̃_j = p_0 ∥ p_j, so a general habit written once in p0 reaches every specialist); S — skill pool (short procedures for classes of sub-problems — algorithm, rule system, pitfall checklist, format convention — indexed by a one-line "when to use" description; the controller sees only the index, the sub-agent receives the full text).
- Step-wise synthesis with overflow decomposition: the controller emits an ordered plan (each step names an agent, a subtask, assigned skills), dispatches ONE step at a time, reads the output, then continues, revises or terminates. Each sub-agent receives the task, its subtask, its skills and a controller-curated summary of earlier outputs (small context). When a step exhausts its sub-agent (context window full or rounds spent), EMMA reads this as evidence the subtask was specified too coarsely — not that the agent failed — and applies overflow decomposition: split the unfinished step into smaller steps over existing agents using the partial trace, splice them into the plan, resume at the same position with completed work preserved. Every overflow is recorded as evidence for the reflector.
- Training loop (attempt chain): each task runs in a fresh environment, gated by its own correctness signal (LLM judge, unit tests or exact match). Correct ends the chain. Incorrect triggers structured reflection in a fixed four-step procedure: localize the failing step → classify into one of five scopes (execution_slip — knew the method, slipped once; agent_behavior — a general working habit failed; procedure — the method for a class of sub-problems is wrong/missing; missing_capability — no agent in the pool can do this work; routing — subtasks correct but decomposition/dispatch wrong) → generalize the correction to every task of the same kind, naming no entity or answer of this task → minimize to the smallest change within the lesson's scope. Ownership rules: execution_slip → plan directive for this task only (REVISE_PLAN/NO_CHANGE, never written to durable memory); agent_behavior → agent prompt (REFINE_PROMPT, in p0 if general); procedure → skill pool (REVISE_SKILL/CREATE_SKILL); missing_capability → skills then agents (CREATE_SKILL/CREATE_AGENT); routing → controller memory (MEMORY_NOTE/REVISE_PLAN; CREATE_AGENT on overflow).
- Guarded update — five programmatic guards, never depending on the backbone: scope–action compatibility (the action is one of Act(z)); prompt preservation (a prompt change keeps most of the existing prompt and may only touch an agent that ran in the failed attempt); bounded memory growth (pools and entries stay within fixed sizes; a new agent must be a genuine specialization, not a duplicate or a label); no leakage (no artifact may contain the reference answer or copy a span of the task text); change of strategy (no memory level edited in more than two consecutive failed revisions; if the same step overflows twice in a row, the action must change how the work is split). A refused proposal returns its reason to the reflector, which retries; persistent refusals default to no change. A newly created or revised skill or agent is named in the re-run's plan, so the edit is actually exercised.
- Re-run until success or the revision budget is spent; NO edit after the final failure (an edit never re-run is untested memory). An end-of-task chain-aware controller update records a few routing lessons. One pass over the training set in fixed order; memory snapshotted after each chain and frozen after the pass — one artifact per benchmark and backbone, no checkpoint selection. At inference the controller keeps memory selection, replanning and overflow decomposition, but no reflector is called and nothing is written.

## Key Findings
- Benchmarks: KramaBench (28 train / 76 held-out; data extraction, integration and analysis across six scientific domains; macro accuracy over domains); AppWorld (90 train / 168 test_normal / 417 test_challenge; tasks across nine applications via APIs, challenge tasks need an application unseen in training; TGC (task-goal completion) and SGC (scenario-goal completion — all variants of a scenario must pass) from state-based unit tests); BBEH-mini (92 train / 368 held-out; 23 equally sized reasoning categories; accuracy). Backbones: Claude Opus 5, Sonnet 5, GLM-5, DeepSeek v3.2, Kimi-K2.5 (controller, sub-agents and reflector share one backbone per run). Baselines: ACE (curated playbook for a fixed ReAct agent), GEPA (reflectively optimized prompt evolution), EvoMAS (evolution of whole multi-agent configurations rewarded by the dataset evaluator minus a cost term), ADAS (meta-agent search over agent programs, budget matched to GEPA).
- RQ1 effectiveness: EMMA attains the best mean on every benchmark — KramaBench 0.654 vs GEPA 0.584 (+7.0 points); BBEH-mini 0.663 vs 0.605 (+5.8); AppWorld normal +11.9 TGC / +17.4 SGC and challenge +6.4 TGC / +5.3 SGC over ACE (EMMA means: normal 84.2/71.0, challenge 73.8/56.0; Opus 5: normal 96.4/94.6, challenge 89.2/83.5). First in 17 of 20 benchmark–backbone settings, second in the other three (KramaBench and AppWorld challenge on Kimi-K2.5, BBEH on Sonnet 5); the runner-up changes with the benchmark (GEPA on KramaBench and BBEH, ACE on AppWorld), so the advantage does not rest on one weak comparison. Largest gains on AppWorld challenge with open-weight backbones (+16.6 TGC DeepSeek v3.2, +15.4 GLM-5).
- Cross-family consistency: (i) multi-agent search methods are the most backbone-sensitive — on AppWorld challenge EvoMAS and ADAS approach EMMA with Opus 5 (89.0 and 84.4 vs 89.2 TGC) but fall to 7.2 (EvoMAS, GLM-5) and 0.5 (ADAS, DeepSeek v3.2); on two open-weight backbones ADAS finds no program better than its hand-written seed. (ii) EMMA's weakest backbone is stronger than every baseline's weakest backbone on every benchmark (58.5 KramaBench, 61.2 TGC AppWorld challenge, 56.3 BBEH), and on KramaBench and AppWorld normal it even exceeds every baseline's five-backbone mean. (iii) EMMA's margin grows on open-weight backbones: AppWorld +0.2 TGC with Opus 5 vs +15.4 (GLM-5) and +16.6 (DeepSeek v3.2); BBEH +2.4 with Opus 5 vs +9.0 (GLM-5) and +10.9 (Kimi-K2.5); on KramaBench a steady shift of about six points on four of five backbones.
- Update efficiency (Table 4, mean over five backbones, lower is better): training executions KramaBench ACE 96.8 / GEPA 156.4 / EvoMAS 280.0 / ADAS 141.4 / EMMA 61.8; BBEH 192.6 / 222.8 / 385.1 / 200.0 / 159.6; AppWorld configuration 283.4 / 229.8 / 1098.0 / 206.0 / 127.8 — EMMA uses the fewest executions on every benchmark, 17–38% fewer than the most efficient baseline (KramaBench −36%, BBEH −17%, AppWorld −38%), because it re-runs only failed tasks and each re-run tests one localized, guarded edit.
- Ablations (KramaBench, Claude Opus 4.5; full EMMA 0.647): memory levels — controller memory learned only 0.506 → + learned skills 0.591 (the larger gain: much transferable knowledge concerns HOW recurring classes of sub-problems are solved) → + learned agent pool 0.647 (specialized agents capture knowledge skills alone do not; controller memory's individual contribution is not isolated since it is learned in every arm). Episodic learning vs test-time adaptation: DACode 0.443, Reflexion 0.476, smolagents DeepResearch 0.535, EvoMAS cross-task self-evolution on the test split without ground truth 0.532 — all well below EMMA 0.647: corrections derived from verified training failures transfer to held-out tasks better than additional adaptation at test time.
- Case study (Sonnet 5 on BBEH): a single failed zebra puzzle produced three artifacts, each at the level that owns it — a constraint-satisfaction skill, a specialist agent created from overflow evidence, and a routing rule in controller memory; subsequent zebra tasks were solved on the first attempt, and a held-out puzzle was solved and verified unique in a single dispatched step.

## Actionable Insights
- The multi-agent configuration itself is memory: instead of fine-tuning or paying experts to design topologies, persist three pools (routing rules / agent prompts / procedural skills) as text and update them from verified failures — apply to multi-channel content pipelines: each channel as a specialist agent inheriting the generalist prompt; a failed article routes to the reflector which assigns a scope (routing vs procedure) and makes one scoped edit. Example: after 28 tasks the system learns the skill "verify factual claims before publishing" plus the routing rule "data-heavy tasks → analytics agent first".
- The 5-scope ownership table + one-edit-per-scope + guards is a discipline applicable even without using EMMA itself: when reviewing a failure of your own agent system, ask "which scope owns this failure (execution / behavior / procedure / capability / routing)" and fix only that layer — avoiding ill-scoped evolution (Opus accumulates skills, DeepSeek spawns agents). Example: a customer-support bot fails because it lacks a tool → scope missing_capability → CREATE_SKILL first, CREATE_AGENT only when skills are insufficient.
- The guards "no edit after the final failure" and "re-run tests every edit" are hygiene rules for any self-improving system: never persist a lesson that has not been re-tested. Example: a pipeline that learns from customer feedback — every new rule must be replayed on the task it failed before being saved to production memory.

## Assumptions & Limitations
- Conditions for the method to work: tasks need an automatic correctness signal (LLM judge / unit tests / exact match) as the gate — domains without an automatic verifier cannot run the loop as-is; training is a single pass in fixed order over 28–90 tasks; memory frozen after one pass with no checkpoint selection; controller, agents and reflector share one backbone per run.
- Acknowledged by the paper: EMMA narrows but does not eliminate the performance gap between backbone families (pairing a strong reflector with weaker executors is a natural way to exploit this — future work); accepted edits persist even when an attempt chain ends unsolved — no systematic degradation observed, but ineffective or harmful entries may remain; cross-verification on mini-batches or multiple epochs could identify them (future work).
- Limitations the paper does NOT state: how generality labels (general/domain-specific/task-specific) are assigned is unclear (likely LLM-assigned — error-prone); the controller chooses memory entries itself ("loading none is valid") — a weak controller can ignore useful memory (double-edged); all benchmarks are agentic coding/data/API tasks — transfer to content/business workflows is unproven (though AppWorld API navigation is close); no confidence intervals reported for the main table; long-horizon memory drift across many tasks is not studied.
