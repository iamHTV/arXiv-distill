# 2610.32338 From Faulty Claims to Incorrect Patches: An Empirical Study of Task-Grounded Reasoning in Coding Agents

## Problem
- Coding agents increasingly resolve real-world software engineering tasks, yet still fail silently: they submit plausible patches that pass their own validation but do not implement the intended behavior. Prior work analyzes trajectories through task-agnostic patterns — repeated actions, untested fixes — describing HOW an agent behaves, not WHAT it misunderstands.
- Gap: an agent can follow an exemplary workflow free of such patterns and still produce an incorrect patch by acting on a faulty task understanding — an incorrect belief about how the existing code behaves, what the task requires, or how a fix meets the requirements. Detecting this requires checking the understanding against the task itself, which prior work has not done. The native chain of thought (CoT) of reasoning models is the only observable proxy of task understanding, but no one had verified each CoT claim against evidence and traced causal links to patch defects.

## Contribution
- The first empirical study of task-grounded reasoning (TGR): CoT claims whose truth is checkable against authoritative evidence (the task statement, the repository at its base commit, library documentation). Method: decompose the CoT into atomic reasoning units, classify them into four types (O original implementation / G implementation gap / S semantic constraint (requirement) / F fix mechanism), let an assessment agent gather evidence and judge each unit supported/refuted/unresolved (FEVER-style fact verification); refuted units are faulty claims. Manual tracing links patch defects to key faulty claims, and trajectory replays with the claim corrected right before submission confirm causality.
- Scale: 400 trajectories of four open-weight reasoning models from two families (DeepSeek-V3.2, DeepSeek-V4.1-Flash, Qwen3.6-27B, Qwen3.8-27B) running in mini-swe-agent on 100 SWE-bench Pro instances; 76,537 reasoning units from 28,001 steps; extraction and assessment by GPT-5.6-Luna; manual validation Cohen's κ 0.937 (extraction) / 0.877 (assessment), precision 86.3%.

## Method (core summary)
- Extraction (§2.3): per-step CoT → LLM produces a normalized claim, a verbatim quote, a type, and referenced files; quote mismatches trigger one retry. Validation on 300 sampled steps (2,149 units): 93.3% correct, 2.9% not reasoning units, 3.8% wrong type.
- Assessment (§2.4): an assessment agent (mini-swe-agent + GPT-5.6-Luna, reasoning effort max) runs in a fresh container with the original repository at the base commit; it never receives trajectory observations, the generated patch, the oracle patch, or test results, so judgments rest only on evidence it gathers itself. Four tools: shell (inspect repo, run tests), documentation fetcher, citation recorder (exact source excerpts), submission. Per-type instructions: O traces code behavior; G compares implementation against requirement; S reconstructs the requirement and searches for a distinguishing input; F searches for a counterexample. Verdicts: supported / refuted / unresolved.
- Tracing (§2.5): two authors read the corrective patch (the edit that, applied on top of the incorrect patch, passes all validation tests while meeting the requirements) and identify key faulty claims (faulty claims whose correction would have given the agent a chance to avoid the defect). They replay each trajectory up to just before submission, send a user message correcting the claim, and have the agent revise and resubmit; the new patch's diff is compared against the targeted fix and validation tests are rerun. Replaying up to submission (not from the error step) keeps the final patch comparable to the original.

## Key Findings
- RQ1 prevalence: TGR covers only 18.5% of CoT tokens (4,593 of 24,784 average per trajectory) yet holds 191.3 reasoning units per trajectory (6.7 per TGR-containing step); 40.7% of steps (28.5 of 70.0) contain TGR. Newer models think 3.6–3.8× longer (Flash 3.79× V3.2 tokens; Qwen3.8 3.60× Qwen3.6) but TGR grows only 2.24–2.58× in tokens and 1.88–2.11× in units — only 12.0% (Flash) and 15.1% (Qwen3.8) of the additional tokens are task-grounded. Type composition: O 43.9%, S 31.9%, F 22.0%, G 2.3%. TGR is front-loaded: token coverage peaks at 29.3% in the second trajectory tenth and falls to 11.9% in the last; 61.3–77.0% of F units lie in the first half (30–49 of 100 trajectories already contain an F claim in the first tenth — mechanisms taken from the task statement before exploring code, e.g. navidrome-0488fb9 Qwen3.6 step 1 of 63); S claims make up half of the final tenth's TGR tokens (6.0% of 11.9%).
- RQ2 faulty claims: the assessment agent refutes 8,540 of 76,537 units (11.2%); estimated error rate 9.6% (a lower bound — recall unchecked); 391 of 400 trajectories (97.8%) contain at least one faulty claim (V3.2: 100%; Qwen3.6 the fewest: 93 of 100); mean 21.4 faulty claims per trajectory (median 14). Newer models resolve more tasks but make MORE faulty claims: Flash 2,865 vs V3.2 1,789 (+60%) despite a lower error rate (10.1% vs 13.3%); Qwen3.8 2,707 vs 1,179 (2.30×), error rate 9.8%→12.0% (composition shift alone would give 11.7%). Error rate by type: O 13.5%, F 14.7%, S 5.5% (lowest in every model, 4.8–8.1% vs ≥10.2% for other types) — agents understand requirements better than code. Error forms (confirmed sample): Misstatement 53.3%, Overgeneralization 24.7%, Misreference 11.3%, Omission 10.7% — only about 1 in 9 faulty claims refers to a wrong or nonexistent object; 59.0% of O errors are misstatements (one third of ALL confirmed faulty claims). Two thirds of S errors are scope errors (overgeneralization/omission).
- RQ2 ↔ outcomes: unresolved trajectories contain 25.2 vs 17.9 faulty claims — mostly because they contain more claims overall (Flash: 1.97× faulty claims but 1.62× units); the error rate is only 0.9–2.1 points higher; on the 38 tasks where models disagree, +1.9 points on average with 95% bootstrap interval [−0.2, +4.0] — NOT significant. 96.7% of resolved trajectories (205/212) still contain faulty claims — the agent later recovers (evidence contradicts the claim) or the patch does not depend on the claim. The two trajectories with the most faulty claims (128 each) both resolve.
- RQ3 causal tracing: 127 of 188 unresolved trajectories (67.6%) contain at least one key faulty claim (V3.2 77.2%, Flash 66.7%, Qwen3.6 57.1%, Qwen3.8 69.2%); 182 key claims in total (80 trajectories with one, 47 with two to four). Type split: O 69 (37.9%), S 61 (33.5%), F 50 (27.5%), G 2. Only about 1 in 26 faulty claims is key: 4,741 faulty claims in unresolved trajectories (25.2 per trajectory) vs 182 key (about one per trajectory); manual sample 17 of 452 (3.8%). The assessment agent refutes 150 of 182 key claims (82.4%) — it detects most but buries each among ~26 other faulty claims.
- Replay outcomes (per-claim corrections, 182 replays): targeted fix produced in 162 (89.0%); more validation tests passed in 34 (18.7%); task resolved in 21 (11.5%) — in 129 replays the defect is fixed but tests do not show it (tests do not exercise the fixed behavior, or other defects remain). Multi-claim trajectories: 91 of 102 single corrections fix the linked defect but only 9 (8.8%) resolve (vs 12/80 = 15.0% for single-claim trajectories); correcting ALL key claims in one message: 19 of 47 (40.4%) pass more tests, 10 (21.3%) resolve. Across all 127 trajectories: 37 (19.7%) pass more tests, 22 (11.7%) resolve; the four models' resolution rate would rise from 53.0% to 58.5%. Targeted fixes are only 40.1% of the corrective patch's changed lines — remaining defects come from edits beyond or contradicting the reasoning (navidrome-66b74c81: hunk header declares 77 lines but the hunk has 81 → truncated file, build fails; openlibrary-25858f9f: function moved but never added to the new module → import failures).
- Agents act on corrections with small, focused edits: median 17 further steps; revised patch differs by a median 13 lines vs the original patch's median 101. Newer models follow corrections more reliably: Flash and Qwen3.8 produce the targeted fix in 100% of replays; V3.2 77.0%, Qwen3.6 87.2%. In about half of the 20 replays without a targeted fix the agent leaves the defective code untouched; three replays (all V3.2) resubmit the original patch unchanged. openlibrary-09865f5: Qwen3.6 swaps to_dict() for dict(obj) — one wrong API for another.
- Resolved does not mean correct: plausible patches pass tests yet are wrong — qutebrowser-a84ecfb (the agent narrows the task to what it expects to be tested; the faulty claim is stated explicitly in the reasoning); qutebrowser-5e0d6dc (a "tests won't check" shortcut keeps an assignment making Array.prototype.at visible to for...in loops).

## Actionable Insights
- Audit CoT claims before trusting a patch (works with models exposing native CoT, i.e. open-weight): extract O/G/S/F claims with quotes, verify each against the repository + task statement + library docs, and fix only the claims the final patch still builds on (key claims) — 96.7% of resolved trajectories also contain faulty claims (presence is a weak signal) and only ~1 in 26 faulty claims causes a defect. Apply: before merging an AI-agent's bug fix for your shop's checkout, run a verification pass on claims like "function X already does Y" by reading the code and probing behavior (execution probes) — not just identifier lookup, since misstatements (53.3%) dominate misreferences (11.3%).
- A correction message right before submission works: 89.0% targeted-fix rate with a median 13-line revision (no rewrite). Apply: in a coding-agent CI pipeline, when a checker refutes a claim, send the correction and require a revision, then run targeted tests for the fixed behavior — the validation suite alone misses 129 of 162 fixed defects.
- Anti-pattern scanning of reasoning flags risky patches: hedged claims ("Probably exact", "likely") and shortcut statements ("tests won't check") mark patches for human review even when tests pass, because agents narrow tasks to what is tested. Apply: add a grep-style rule to a review bot that queues patches whose CoT contains "won't check" or "probably" for manual review.

## Assumptions & Limitations
- Conditions for the method to work: native CoT must be accessible (open-weight models) — commercial models usually hide the native CoT (limits direct application; agent-framework thoughts are a poorer substitute); a fixed scaffold (mini-swe-agent) and benchmark (SWE-bench Pro); evidence sources must exist (task statement, base-commit repository, library docs).
- Acknowledged by the paper: assessment-agent recall unchecked (error rates are lower bounds; but it refutes 82.4% of key claims); manual validation on samples only (300 steps, 40 trajectories — yet exceeding the 99% confidence ±5% margin sizes: 2,149 of 76,537 units vs 660 required; 896 of 8,540 faulty claims vs 618 required); only open-weight models, a single scaffold, a single benchmark; dependencies among faulty claims and why models make them unstudied (black box).
- Limitations the paper does NOT state: the corrective patch is built by the authors themselves (gold standard) with no reported inter-annotator agreement for defect localization and replay judgments; the replay timing is unrealistic (correction sent right before submission — production cannot know in advance); the key-faulty-claim definition is counterfactual and subjective ("had the claim been corrected, the agent would have had a chance"); the cost of running the assessment agent at scale is not reported; the 53.0% base resolution (212/400) means conclusions are drawn from a population that already fails half the tasks — transfer to stronger scaffolds is unclear.
