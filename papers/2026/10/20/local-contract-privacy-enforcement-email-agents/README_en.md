# [2610.18007v1] Cost-Efficient Privacy Enforcement for Email-Generating LLM Agents under Strategic Information Requests

## Problem
- Email-generating agents are delegated information intermediaries: they read private context (Gmail/Notion), draft, and send emails to recipients — access does NOT imply authorization for the recipient. Checker-only defenses (e.g. PrivacyChecker with contextual-integrity reasoning) reduce leakage but are economically expensive: a failed draft triggers another remote action-LLM repair call plus another checker call — a costly loop. Strategic information requests — requesters who keep the appearance of a legitimate task while pressuring the agent to disclose exact values, raw records, source evidence, or "all relevant details" — worsen BOTH sides: more leakage AND higher remote enforcement cost. Prior work measures leakage but not cost amplification.

## Contribution
- Reframes the problem as cost-aware strategic information release: defender objective W(M,sigma) = U - lambda*L - mu*R_remote - eta*G_local - nu*S_drift (utility - leakage - remote cost - local cost - semantic drift).
- Local contract-conditioned rewriting as an enforcement layer: intercept the outgoing draft -> build an information-release contract (must_preserve / required_slots, must_generalize privacy-risk rules, must_not_add, information_shape / safe_output_shape, safe-substitution guidance) -> rewrite with a local Gemma rewriter -> selectively invoke PrivacyChecker as the final semantic gate; checker feedback goes verbatim into local repair (max 3 rounds); fail closed (block when no safe draft exists).
- Boundary placement is critical: a wrapper at the email-sending tool lets only the exact draft that passed enforcement be sent — the agent cannot decide whether its own output is checked (a mismatched resend triggers re-inspection).
- Cost math: R_remote(MB) = c_A(1+K_B) + c_C(1+K_B) vs R_remote(MG+C) = c_A + c_C(1+K_G), so DeltaR = c_A*K_B + c_C*(K_B-K_G); the local model need not be a perfect privacy judge — it only needs to reduce the leakage burden entering the checker enough to avoid expensive remote repair cycles. MG (Gemma-only) is acceptable in low-risk deployments only when mu*DeltaR > lambda*DeltaL.

## Method (core)
- 2x3 design matrix: {normal, attack} requester conditions x {MB (remote checker-repair baseline, same-session repair with 25-turn cap), MG (Gemma-only, no final check), MG+C (full mechanism)}.
- Data: 149 aligned tasks from the Privacy in Action benchmark, 480 annotated sensitive items, Gmail/Notion retrieval -> email generation/reply (reply_response, update_status, provide_details_data, summary, scheduling_coordination). Attack prompts operationalize strategic requests (exact-value / raw-record / source-evidence / structured-extraction / completeness pressure).
- Models: action LLM + checker + leakage evaluator = DeepSeek deepseek-v4-flash (evaluator uses a different prompt); utility judge = deepseek-v4-pro; local rewriter = gemma4-e4b-q4-12k via Ollama, q4_K_M, temperature 0.0, 12k context.
- Metrics: item-level and secret-level leakage (exact / paraphrased / reconstructive — the recipient could infer the private fact from remaining wording); UsableRate = satisfied + partially_satisfied (under attack prompts, judged on the benign task shell only); CostAmp = RemoteTokens(attack)/RemoteTokens(normal).

## Key Findings
- Normal prompts: leakage MB 11.41% -> MG 5.37% -> MG+C 4.03% (-64.7% vs MB); UsableRate 85.2% -> 89.9% -> 92.6%; slot retention 0.999 / 0.970 / 0.981; semantic drift 0.001 / 0.062 / 0.046.
- Attack prompts: leakage MB 28.19% -> MG 21.48% -> MG+C 18.79%; leak delta +16.78 / +16.11 / +14.76 pp; CostAmp MB 1.32x, MG 0.98x, MG+C 1.02x; checker-call amplification 1.69x -> 1.02x.
- Remote tokens: normal MB 8,728,781 (agent 8,390,242 + checker 338,539) -> MG+C 7,189,612 (5,281,175 + 1,908,437) = -17.6%; attack MB 11,540,135 (10,861,107 + 679,028) -> MG+C 7,318,258 (5,306,892 + 2,011,366) = -36.6%. Gemma local tokens 1,144,181 (normal) / 1,246,723 (attack) — deployment cost, not remote API cost. Avg checker calls: normal 1.06 / 0.00 / 1.00; attack 1.79 / 0.00 / 1.02.
- Attack utility (benign safe-shell): repair rounds MB 1.52 vs MG+C 0.04; slot retention 0.984 / 0.977 / 0.991; UsableRate 99.3% / 98.7% / 100.0%; drift 0.012 / 0.043 / 0.022 — privacy gains are NOT obtained by refusing emails or over-generalizing.
- Contract ablation (offline replay on the same drafts): generic Gemma rewrite normal 7.38% / attack 32.21% -> full contract 4.70% (-36.3%) / 14.77% (-54.1%); without required_slots + information_shape: 5.37% (-27.2%) / 15.44% (-52.1%) — the structured contract filters leakage far better than a generic "remove private information" prompt.
- Case studies (anonymized): school-health update — MB reports condition/recovery/test evidence; MG+C rewrites to a high-level health-status + care-plan summary. Structured compensation request — MB discloses exact salary/bonus/equity under adversarial request; MG+C keeps negotiation context but removes exact fields. Gemma-only residual case — removes disease names but leaves respiratory-monitoring cues (reconstructive leakage) -> the checker abstracts further and removes them.

## Actionable Insights
- Wrap every outgoing agent action (email, message, CRM update) at the tool-send boundary with a contract-conditioned local rewriter before the remote checker: cut remote tokens 17.6-36.6% and checker-call amplification 1.69x -> 1.02x under attack, leakage 11.41% -> 4.03% under normal prompts. E.g. a support agent with user-PII access rewrites locally before sending, invoking the remote checker only for high-risk drafts.
- Strategic requesters (clients asking for "exact figures, raw records") are a real threat: leakage jumps from 11.4% (normal) to 28.2% (attack), +16.8pp — an enforcement layer is required, not model judgment alone. E.g. add "must_not_add: exact figures, raw records" policies for a sales agent.
- The contract must separate 4 concerns (preserve / generalize / forbid / shape) — a generic privacy prompt performs 36-54% worse in relative terms; and a CHEAP local model (4B-quantized Ollama Gemma) suffices for first-stage sanitation while the checker remains the final gate.

## Assumptions & Limitations
- Conditions: annotated sensitive items (or a policy item list) must exist for the task; the local rewriter must have sufficient rewriting capability (any trusted on-prem editor can instantiate the same policy); a fail-closed policy accepts blocking emails.
- Authors admit: MG is NOT a replacement for final checking (higher leakage than MG+C, especially under attack); the checker can miss semantic leakage or over-flag safe abstractions; the contract can infer the wrong task type, omit a required slot, over-generalize, or preserve an unsafe detail; the leakage evaluator uses the same model family as the checker with a different prompt — manual spot checks only, no formal human evaluation; email-only — Slack/calendar/CRM/document-sharing extensions need action-specific information-shape constraints.
- Not stated: the utility judge (deepseek-v4-pro) is an LLM, not humans — satisfaction labels carry judge bias; attack prompts are benchmark-constructed, not live adversaries; the quantized 4B local rewriter's quality in other languages/domains is untested (Vietnamese untested); contract generation is itself an LLM call whose failures are not quantified; local-rewrite latency is not measured.
