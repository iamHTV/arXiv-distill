# Skill: candidate-supply-answer-selection
Source: 2608.25937v2
Type: framework

## When to use this skill
- A multi-agent system generates multiple candidate answers and needs to select one final answer.
- Want to know when to use an LLM judge to rank candidates instead of plain majority voting.
- Have a fixed candidate bank (or can create one) and want to evaluate judge reliability before deployment.

## When NOT to use this skill
- Correct answers dominate the candidate bank (ppool ≥ 0.25) → majority voting is already reliable; judging can reduce accuracy.
- Assuming judge reliability is a static trait applicable to all tasks and generators.

## Required inputs
- A candidate bank of answer candidates with supporting rationales, generated by agents or repeated generator calls.
- An LLM judge able to rank anonymous candidate rationales (without seeing answers/correctness labels).
- Correct-answer availability pgen (empirical fraction of correct candidates in the bank).
- Bank size k (e.g., k=8) and realized correct fraction ppool.

## Steps
1. Generate the candidate bank: call the generator repeatedly per question, collect answer candidates + supporting rationales; compute pgen (empirical fraction of correct candidates).
2. Run majority vote as the initial readout (t=0): pick the most frequent answer.
3. Run the LLM judge to rank anonymous candidates in the bank; measure rank ASEAN (probability a correct candidate is ranked above an incorrect one).
4. Evaluate judge reliability against pgen: rank ASEAN below 0.5 at low availability means the judge is not trustworthy when correct answers are rare; the half-rise midpoint indicates the pgen level where the judge becomes informative.
5. Apply the terminal-selection rule combining answer frequency and judge ranking (rank-power weight wi = (k−i)^t, t=2–4 for best stability): select the answer combining both signals.
6. Evaluate by bank size: small banks (k=2–6) benefit most from judge selection (+13.52 pp over majority at k=2); large banks (k≥14) make majority voting more competitive and judging more expensive.
7. Stratify by realized ppool: small correct minority (ppool < 0.25) → judge beats majority by a lot (+40.1 pp at k=6); high correct fraction (ppool ≥ 0.25) → majority beats judge (−4.0 pp at k=6).
8. Track cost: judge selection is cost-effective at small banks (US$0.10–0.39 per 1,000 additional correct answers at k=2–6); cost escalates at large banks (US$6.28 at k=14).

## Expected output
- An optimal terminal answer-selection rule (combining answer frequency + judge ranking) that knows when to rescue outnumbered correct answers and when to use plain majority voting; a judge-reliability assessment for the actual deployment regime.

## Example application
- A medical multi-agent QA system: generate 8 candidate answers from 8 agents; run majority vote; run an LLM judge to rank the 8 candidates; combine both (t=3) to select the final answer — giving an outnumbered correct answer a better chance than plain majority vote.

## Gotchas
- Do not use judging when correct answers dominate the bank (ppool ≥ 0.25): majority voting is already good, judging reduces accuracy (−3.22 pp at pgen > 0.625).
- Do not treat a static judge benchmark score as a universal guarantee — judge reliability varies by generator, task and pgen.
- Do not assume generating more candidates always helps — value depends on whether new samples make correct answers present, frequent enough for voting, or leave a minority an informative judge can recognize.
- Do not ignore judging cost — cost escalates quickly at large bank sizes and may not be worth it.
