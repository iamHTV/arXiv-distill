# [2610.11963v1] Can LLMs Fix It Without Code? Toward Automated Verification of No-Code Bug Fixes

## Problem
- Bug reports requiring no source-code change ("invalid reports": user misconfiguration, outdated version, conflicting extension, misunderstanding) make up a substantial share: a manual inspection of 7,000+ reports across five open-source projects found 33.8% of bug-labeled reports misclassified (Herzig et al.); an industrial case study found 14-17% of submitted reports invalid yet still taking 16-18 calendar days to resolve — about as long as valid reports despite requiring no code change (Laiq et al.). Prior evaluation of LLM-generated "no-code fixes" (directing the user to change a setting, update to a fixed version, or adjust workflow) uses only text similarity (BERTScore in a narrow 0.81-0.82 band across all models) + an LLM judge — neither shows whether a fix WORKS when a user follows it; the LLM judge inherits documented biases. Gap: execution-based verification for no-code fixes — apply the fix in a real environment and check whether the symptom persists or disappears (like SWE-bench for code patches, but never done for no-code fixes, and never with executor choice treated as an experimental variable).

## Contribution
- Rollback-based, execution-driven pipeline: for each bug report (1) apply the maintainer's ground-truth fix, (2) scripted sanity gate #1 (bug ABSENT on the fixed state), (3) scripted rollback -> buggy state, (4) scripted sanity gate #2 (bug PRESENT on the buggy state), (5) apply the candidate LLM fix via an executor agent acting on the browser GUI, (6) a deterministic issue-specific checker reads the browser state and decides whether the bug remains. Both sanity gates are SCRIPTED (not agent-driven), so environment validity is independent of the executors under study. The executor's own success claim is recorded but NEVER used as the verdict.
- Executor choice treated as a first-order experimental variable: three executors from different providers (two computer-use agents + one multimodal agentic LLM), validated against double-blinded human execution (RQ3).
- 322 fixes evaluated (12 LLM configurations x 3 runs x 9 reproducible issues; Agentic-Kimi has 25 fixes — 2 runs missing for issues 25057/45912).

## Method (core)
- Benchmark: Gön et al.'s invalid Brave browser reports (302 annotated -> 51 candidates in subclasses Faulty Configuration & Environment Setup / Wrong Version (Already Fixed) / External System & Dependency — the 3 subclasses whose resolutions are executable actions; 38 could not be set up in a Linux container (other platform, live backend, missing info), 4 did not exhibit the bug -> 9 effective issues (17.6%). Subclass sizes: Faulty Configuration 5 issues/178 fixes, Wrong Version 1/36, External 3/108.
- 12 configurations = 4 pipelines x 6 backbones: Vanilla (Gemini 3.1 Pro Preview, GPT-5.4, Claude Opus 4.6, GLM-5, MiniMax M2.7, Kimi K2.5); Ablation No-Prior (Gemini, Kimi); RAG (Brave wiki + historical invalid reports, Zembed-1 embeddings in LanceDB, top-20 neighbors per corpus, chronological filtering against data leakage, Zerank-24 cross-encoder reranking -> top-5 contexts; Gemini, Kimi); Agentic Web Search (WebThinker Think-Search-and-Draft, Serper API, canonical original-issue page excluded against leakage; Gemini paired with Gemini 2.5 Flash search loop, Kimi).
- Pipeline mechanics: the ground-truth fix is classified version-type (Docker container running a newer fixed Brave release) vs GUI-type (container on the reported version + maintainer fix applied via GUI). Per-fix episode: fresh container, buggy value pre-seeded for 3 issues; the executor applies the fix in <=20 steps through a shared action interface; on version-type issues, when the executor opens brave://settings/help the harness switches the container to the fixed build (resolution rates on these issues depend on the executor performing the update).
- Executors: OpenCUA-72B (open-weight CUA, greedy T=0), Claude Sonnet 5 with computer use (default sampling), Meta Muse Glimmer-30B (open-weight agentic model driven through a custom function-calling schema — no official computer-use harness; T=1.0, top-p 0.95). Identical task prompt (bug report + fix text).
- Checker: deterministic, issue-specific, reads browser state tied to the reported symptom (preference files via Chrome DevTools Protocol, rendered-page properties) -> is the stated actual result still present? The only issue-specific code in the pipeline (released in the replication package).
- Aggregation: a fix counts as resolved if the checker reports the bug absent in >=1 of 3 runs (episodes are stochastic; a failed run may reflect executor error); non-applicable if the executor declared BLOCKED in >=2 of 3 runs. 3 runs per fix per executor.
- Human validation (RQ3): 75 of 322 fixes randomly sampled (fixed seed; 95% confidence, ±10% margin via Cochran's formula with finite-population correction, p=0.5); two author-executors double-blinded (they see neither the generating configuration nor any agent outcome); they execute each fix "literally" (without judging correctness) on the identical buggy starting state; executor resolved-verdict vs human outcome compared with Wilson intervals and Cohen's kappa.

## Key Findings
- RQ1 overall (322 fixes): resolution rate 49.7% (Sonnet 5, 160 fixes), 45.7% (OpenCUA-72B, 147), 14.6% (Muse Glimmer, 47); applicability 66.1%/99.1%/70.5% (213/319/227); resolution among applicable fixes 69.5%/45.8%/18.1% (148/146/41).
- V-Claude (Claude Opus 4.6, Vanilla pipeline) strongest under Sonnet 5 at 74.1% (also highest applicability 88.9%) — but NOT stable: third under OpenCUA (51.9%, tied with V-Gemini), second under Muse Glimmer (25.9%). Under OpenCUA, RAG-Kimi and Agentic-Gemini tied first at 55.6%; under Muse Glimmer, Agentic-Kimi led at 28.0%. Lowest per executor: 25.9% V-MiniMax (Sonnet 5), 33.3% V-Kimi (OpenCUA), 0.0% V-Kimi (Muse Glimmer).
- Backbone-fixed pipeline comparison: Gemini — Agentic highest under both Sonnet 5 (63.0%) and OpenCUA (55.6%); Kimi — Agentic highest under Sonnet 5 (56.0%), RAG highest under OpenCUA (55.6%). RAG-Kimi vs V-Kimi under OpenCUA: 55.6% vs 33.3% (+22.3pp) but EQUAL under Sonnet 5 -> pipeline-enhancement benefits are EXECUTOR-DEPENDENT.
- Per subclass: Faulty Configuration best under OpenCUA 65.7% (Sonnet 5 43.8%, Muse Glimmer 13.5%); External System best under Sonnet 5 59.3% (OpenCUA 25.0%, Muse Glimmer 21.3%); Wrong Version (single issue): Sonnet 5 50.0%, OpenCUA 8.3%, Muse Glimmer 0.0% (Sonnet completes the update plus the gradient selection this issue requires).
- RQ2 executor sensitivity: within-executor run spread <=3.4 points (Sonnet 5 38.8%-42.2%) — differences BETWEEN executors exceed run-to-run variation (systematic, not noise); a single configuration's resolution rate differed across executors by 38.8% on average (range 25.9-48.1, 95% bootstrap 31.2-52.1); all three executors reached the same verdict on only 46.9% of fixes; pairwise agreement 62.4%/64.3%/67.1% (kappa = 0.25/0.28/0.30); configuration rankings Kendall tau-b 0.13 (Sonnet-OpenCUA), 0.45 (Sonnet-Glimmer), 0.05 (OpenCUA-Glimmer) — nearly unrelated; excluding the 3 version-dependent issues, agreement drops further (kappa 0.22/0.24/0.17; all-agree 40.7%).
- Run-level: all three runs agreed on 82.3% (Sonnet 5) / 73.9% (OpenCUA) / 92.2% (Muse Glimmer) of fixes; any-run aggregation added fixes: 160 vs best single run 136 (Sonnet 5), 147 vs 109 (OpenCUA — the least stable executor, +38), 47 vs 35 (Muse Glimmer +12); majority vote 39.8%/30.7%/9.9% — ordering unchanged.
- Per-issue extremes: on 37372 OpenCUA resolved ALL 36 fixes (lenient checker: the expected value is the browser default, which is not stored explicitly, so the checker accepts absence of the preference — a general settings reset counts as resolution) vs Sonnet 5 20 and Muse Glimmer 12; on 24747 Sonnet 5 resolved 19 while OpenCUA and Muse Glimmer resolved 0; on version-dependent issues Sonnet 5 resolved most (16/18/29 for issues 22252/25379/31108); on 25379 OpenCUA resolved 3 (an update alone is insufficient — a gradient must be chosen afterwards) and Muse Glimmer 0; Muse Glimmer resolved ZERO fixes on issues 24747, 25057, 25379, 45912.
- Termination signals are not the verdict: explicit-verdict episodes Sonnet 5 83.0% (50.2% DONE, 32.8% BLOCKED), OpenCUA 59.7% (55.1% DONE, 4.7% BLOCKED), Muse Glimmer 44.9% (13.4% DONE, 31.6% BLOCKED); step-budget exhaustion 16.3%/40.2%/55.1%. The checker found the bug resolved in 621 of 1,146 DONE episodes (54.2%), 162 of 1,077 budget-exhausted episodes (15.0%), and 18 of 667 BLOCKED episodes (2.7%) — 45.8% of DONE episodes failed while 15% of exhausted episodes still resolved. On version-dependent issues, Sonnet 5/OpenCUA/Muse Glimmer said DONE while the checker failed in 7/121/1 of 324 episodes, and the checker passed without a DONE report in 54/38/26. Using the agent's own completion signal would both inflate and deflate the measured capability.
- RQ3 humans: the two authors agreed on 78.7% of the 75 sampled fixes (kappa = 0.54); human 2 resolved more than human 1 (29 vs 25). Executor agreement with the human consensus: Sonnet 5 88.1% (kappa = 0.74), Muse Glimmer 79.7% (kappa = 0.48), OpenCUA 66.1% (kappa = 0.28). Mismatch direction: OpenCUA's 20 mismatches -> 13 FALSE POSITIVES (counted as resolved although humans did not); Muse Glimmer's 12 mismatches -> 10 FALSE NEGATIVES (did not resolve although humans did — consistent with 55.1% budget exhaustion); Sonnet 5 erred in both directions (5 FP, 2 FN). Sample resolution counts: Sonnet 5 33, OpenCUA 33 vs humans 25/29 — Sonnet 5 and OpenCUA OVERSTATE, Muse Glimmer UNDERSTATES. Majority vote: 86.4%/72.9%/81.4% (ordering unchanged, <=6.8% change).
- BERTScore analysis (Section 5.2): the 108 fixes that failed ALL nine attempts (every run, every executor) scored BERTScore F1 0.757-0.867 (median 0.831) — within or ABOVE the 0.81-0.82 range Gön et al. report for fixes overall; the 214 fixes at least one executor resolved scored the SAME (median 0.832, mean 0.824 vs 0.823); scores varied more between issues than within them (issue 25379 averaged 0.762 vs 0.818-0.846 for others) -> similarity reflects the wording of the reference resolution, not fix correctness; a single threshold cannot separate working from failing fixes.
- Scarcity finding (Section 5.4): 302 annotated reports -> 51 candidates -> 9 executable issues — no-code fixes are frequently entangled with state the report does not capture (accumulated user profile, OS/hardware configuration, third-party service behavior at report time, server-side changes no local rollback can undo); issue trackers leave NO structural trace (invalid reports are unlabeled, resolutions are not linked to commits), so dataset construction itself becomes a research problem (automate recognition of no-code resolutions in maintainer comments).

## Actionable Insights
- Never send LLM-generated no-code fixes to users unverified: even the best executor (Sonnet 5) resolved only 49.7% of fixes (39.8% under majority vote); the best configuration reached 74.1%. E.g. a support bot telling a user "update Brave and select gradient X" for a reported error — verify inside a Docker pinned build with an execution pipeline before sending; only send checker-confirmed fixes.
- Run execution-based evaluation with >=2 executors and calibrate against humans: executor choice shifts measured capability by 38.8% on average, config rankings sit at tau-b 0.05-0.45 (nearly unrelated), and all-three agreement is only 46.9% — one executor is not a neutral instrument. E.g. when evaluating your QA agent, run both a Claude-class computer-use model and an open-weight CUA; if the OpenCUA-style executor agrees with humans at only 66.1% (13/20 mismatches are false positives), use a Sonnet-class executor (88.1%, kappa 0.74) as primary and calibrate with a 75-fix double-blinded human sample.
- Separate the executor's signal from a deterministic checker: the agent saying DONE does not mean the bug is gone (45.8% of DONE episodes failed while 15% of budget-exhausted episodes still resolved) — never use the agent's own completion claim as the verdict. E.g. in your fix-verification pipeline for a retail app, the checker reads app state through a debug protocol while the agent only applies the fix; and build the two scripted sanity gates (bug absent on the ground-truth-fixed state, present on the rolled-back state) before trying candidate fixes.

## Assumptions & Limitations
- Conditions: the bug must be re-establishable in a controlled Linux browser environment (only 17.6% of candidates passed the gates — version-type or GUI-type fixes on pinned builds); a deterministic issue-specific checker is needed per report (the only issue-specific code); human time for double-blinded calibration.
- Authors admit (threats): executors may misapply, partially apply, or change unrelated state; the 20-step budget can cut off episodes that would have succeeded (Muse Glimmer 55.1%); harnesses are NOT identical (Sonnet 5 native computer-use, OpenCUA own action format + screenshot history window, Muse Glimmer custom function-calling schema -> RQ2 compares executors WITH their harnesses); sampling settings differ (OpenCUA greedy T=0; Muse Glimmer T=1.0 top-p 0.95 — higher temperature benefits more from any-run aggregation); checker validity (issues 25057/37372 lenient — a general settings reset counts); applicability depends on executor judgment (OpenCUA ended only 4.7% of episodes BLOCKED); buggy-state fidelity (2 reports state no version -> a nearby pinned build was used); human executors are the authors (blinded, but moderate agreement kappa 0.54, consensus set contains only 19 resolved fixes, intervals wide, NO significance tests); single application (Brave) + single benchmark + 17 of 51 platform-specific candidates excluded; the Wrong Version result describes a SINGLE issue.
- Not stated: only 9 issues total -> subclass breakdown (5/1/3 issues) is underpowered (Faulty Configuration vs External comparisons are descriptive); Docker/Linux-only — Windows/macOS-specific invalid reports (17 excluded) systematically differ from those evaluated; executor cost per episode (OpenCUA-72B 72B-parameter inference across 322 fixes x 3 runs x 3 executors ~ 2,898 episodes) — no real-world deployment cost measurement; fixes encode Brave product knowledge only — generalization to other apps unstudied (noted as future work); no improvement directions for no-code fix GENERATION quality beyond pipeline variants (RAG/Agentic gains inconsistent); the human "execute literally" protocol means humans do not judge fix correctness, so ambiguous fixes admitting multiple readings inflate mismatch rates; any-run aggregation inflates the least stable executor (OpenCUA +38) — cross-executor comparisons under the any-run rule are biased toward volatile executors.
