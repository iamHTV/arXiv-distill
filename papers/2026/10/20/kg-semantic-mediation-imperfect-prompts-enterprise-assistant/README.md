# [2610.23304v1] Designing for Imperfect Prompts: A Simulation-Based Evaluation of an LLM-Based Enterprise Data Assistant Using Knowledge Graphs

## Problem
- Enterprise data assistant (assistant dữ liệu doanh nghiệp dùng LLM) deployed real tại CFO unit data lake (industry partner): business users đặt imperfect prompts (prompt không hoàn hảo) — cực ngắn (trung bình 1,14 câu, ~10 words), KHÔNG reference schema (table/column names, keys, KPIs), chỉ nêu high-level goals. 0/158 interactions chứa explicit schema reference; all short single-intent. Assistant không infer reliably entities/measures/relationships → guess hoặc default sang superficially plausible nhưng sai columns/joins; failure pattern recurrent: anchor on similarly-named attributes thay vì reconstruct structural logic. Ví dụ VAT fiscal unity: concept đúng cần discovery subsidiaries + shareholders + join paths tới hierarchy/ownership tables, nhưng assistant dùng cột VAT fiscal unity state làm proxy; term "fiscal unity" polysemous (income-tax vs VAT fiscal unities) — expert disambiguate dễ, assistant thiếu cues. Mitigation cycle 1 (router 3 subagents + vector-store ≥2 few-shot examples/table) brittle + labor-intensive: only previously modeled cases benefit → unsustainable at enterprise scale.

## Contribution
- Semantic mediation layer (lớp trung gian ngữ nghĩa) cho enterprise data assistant: transform brief goal-oriented prompts thành database-grounded inputs mà KHÔNG burden user với schema knowledge hay operational overhead. Yêu cầu: (1) preserve user intent — original goal/scope/constraints không lost/altered, (2) knowledge grounded — enrich prompts với domain+data semantics, (3) lightweight — automatic, low-maintenance.
- Hai design variants so sánh: schema-based mediation (retrieve table schemas trực tiếp bằng semantic similarity — baseline nhẹ) vs KG-based mediation (knowledge graph tự xây từ database schema: nodes tables+columns, edges has_column + joins_on từ PK-FK hoặc heuristics name-matching/type-compatible; captures direct + indirect joins).
- Design principle (DSR format Aim/Context/Mechanism/Rationale): artifact nên incorporate KG-based mediation layer operating on và augmenting user prompts — giảm dependence on manual prompt engineering, bridges intentional goals vs system representations.

## Method (tóm tắt cốt lõi)
- KG tự xây bằng NetworkX 3.5 từ Databricks Information Schema: 273 nodes, 540 edges trên database partner; nodes lưu ChromaDB 1.3.4 với OpenAI text-embedding-3-large (vector-store semantic matching user phrasing → canonical KG nodes). KG deliberately KHÔNG include domain constructs (specialized metrics, fine-grained filters) — isolate structural knowledge contribution.
- Pipeline 3 bước: (1) segment user prompt thành distinct intent units; (2) similarity_search per segment → entry nodes, retrieve table→all columns + column→parent table; (3) traverse KG direct + indirect join paths → subgraph (avg 54 nodes SD=30, 99 edges SD=41/query) → LLM refine prompt (GPT-4.1 hoặc Claude Sonnet 4) integrating retrieved knowledge. Schema-based: retrieve 91 columns avg (SD=19) trực tiếp.
- Evaluation: real enterprise log-data N=158 interactions, N=29 users CFO unit (30 days gần nhất; assistant available 6 months nhưng chỉ 30 days logs lưu). Hai approaches: LLM-as-a-Judge binary Completeness (COMPLETED/NOT COMPLETED theo Alabool 2025, 3 few-shot examples, Pydantic structured output) + human validation (2 data analysts từ partner, 2 iterations — analyst 1 review, analyst 2 review results, so sánh + discuss + resolve conflicts → Precision/Recall/F1 từ TP/FP/FN). Control TN checks với non-database prompts. Preliminary end-to-end test 30 interactions random subset.

## Key Findings
- GPT-4.1: KG Precision 90.67% (Schema 69.05%, +21.62pp), Recall 88.31% (Schema 73.11%, +15.20pp), F1 89.47% (Schema 71.02%, +18.45pp); Completeness 93.04% (Schema 89.24%, Baseline 91.14%) — KG PRESERVE intent TỐT HƠN baseline ngay cả khi expose thêm database content.
- Claude Sonnet 4: KG Precision 87.23% (Schema 75.17%, +12.06pp), Recall 93.52% (Schema 92.56%, +0.96pp), F1 90.29% (Schema 82.17%, +8.12pp); Completeness 86.45% (Schema 84.52%, Baseline 85.33%).
- Annotator agreement: 98.73% (KG) / 98.10% (Schema) GPT-4.1; 95.57% (KG) / 96.84% (Schema) Claude Sonnet 4.
- Processing time: schema 1.1s avg vs KG 2.7s avg. KG retrieval avg 54 nodes (SD=30) + 99 edges (SD=41)/query vs schema 91 columns (SD=19). Word count: GPT-4.1 mediated M=29-30 (schema/KG) vs baseline M=18; Claude M=33-37 vs baseline 17 (KG surfaces explicit join specs).
- Demo case "Which audit requests and findings still need to be completed, including company name and ID?": KG correctly identifies audit_single_issues.issue_done=FALSE + join basis_info on unit_id (21 nodes, 30 edges); schema-based picks same 3 tables + 76 columns nhưng CHỌN SAI → wrong prompt "Search the audit_status table for P8A_AUDIT_NAME" (audit period level, không phải individual requests + companies).
- End-to-end preliminary (30 interactions): TP prompts proceed KHÔNG cần additional schema discovery (giảm latency); FN cases cần explicit schema lookup hoặc broader results cần narrowing; higher F1 correlate với higher end-to-end accuracy; schema-based prone erroneous/hallucinated joins trên complex schemas — once encoded vào mediated prompt, downstream query planning + execution RELIABLY FAILS.
- TN control checks: neither approach injected additional/incorrect knowledge trên non-database prompts.

## Actionable Insights
- Trước khi cho business users (non-SQL) dùng data assistant, install KG-mediated prompt augmentation layer (auto-build từ schema — 273 nodes/540 edges trong minutes) thay vì few-shot curation thủ công per table: Precision +12–21.6pp, F1 +8.1–18.5pp cross 2 LLMs. Ví dụ: assistant bán hàng cho manager hỏi "đơn hàng nào chưa giao cho khách VIP" → mediator thêm đúng tables + joins sẵn, assistant không guess.
- Schema-similarity retrieval alone là TRAP trên complex multi-join schemas: hallucinated joins encoded vào prompt → downstream execution reliably fail. Ví dụ: dashboard query cần 3-table join — schema-only trả sai join path → kết quả sai silent; KG traversal (direct + indirect paths) là safeguard tối thiểu.
- "Just-right" context beats large context windows: subgraph ~54 nodes/99 edges outperforms flooding; và mediation KHÔNG làm giảm completeness (93.04% > baseline 91.14%) → mediator là controlled augmentation không phải risk. Ví dụ: prompt refinement pipeline nên inject subgraph nhỏ gọn thay vì toàn schema.

## Assumptions & Limitations
- Điều kiện: database schema có metadata (information schema) + PK-FK constraints hoặc name/type heuristics đủ để build joins_on; vector-store embedding quality đủ để map user phrasing → canonical nodes ("Reliable KG performance depended on identifying the right entities and relations" — database phải thoroughly curated); deployment context enterprise LLM assistant.
- Paper thừa nhận: single-enterprise setting (CFO unit 1 partner), 158 interactions/29 users — generalizability hạn chế; simulation-based (log-data + human annotators) KHÔNG real-time user input — next cycle field deployments + A/B; KG coverage + maintenance cần systematic governance (versioning, change management) production; KG auto-generated lacks domain constructs (metrics, filters); không systematically vary network density; graph structure differs across domains; minimal-change mediation cases (knowledge lack) not captured by completeness metric.
- Limitation paper KHÔNG nói: LLM-as-Judge single-judge bias chỉ mitigated bằng 3 few-shot examples (không multi-judge ensemble); binary completeness label coarse (mid-level quality loss invisible); end-to-end test chỉ 30 samples informal chưa statistical; latency 2.7s vs 1.1s local processing — inference COST không reported (mediation LLM calls mỗi query); baseline completeness 85.33/91.14 paper prose ghi nhầm "schema 85.33%" nhưng table rows cho thấy 85.33% là Claude baseline, GPT-4.1 schema = 89.24% (possible paper typo, dùng table value); embedding model OpenAI → data gửi external (privacy consideration enterprise data lakes).
