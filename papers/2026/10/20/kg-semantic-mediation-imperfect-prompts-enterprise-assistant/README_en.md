# [2610.23304v1] Designing for Imperfect Prompts: A Simulation-Based Evaluation of an LLM-Based Enterprise Data Assistant Using Knowledge Graphs

## Problem
- Enterprise data assistants using LLMs promise democratized data access, but in a real deployment in the CFO unit's data lake of an industry partner, business users pose imperfect prompts: extremely short (average 1.14 sentences, ~10 words), no schema references (table/column names, keys, KPIs), high-level goals only. 0 of 158 interactions contained explicit schema references; all were short and single-intent. The assistant could not reliably infer entities, measures, and relationships, so it guessed or defaulted to superficially plausible but incorrect columns and joins. Recurrent failure pattern: anchoring on similarly-named attributes instead of recovering the structural logic implied by intent. Example: VAT fiscal unity — the correct interpretation requires discovering subsidiaries + shareholders + join paths to hierarchy/ownership tables, but without guidance the assistant used a column with a "VAT fiscal unity state" attribute as a proxy; "fiscal unity" is polysemous in the data lake (income-tax vs VAT fiscal unities). First-cycle mitigation (router to 3 specialized subagents + vector store with >=2 few-shot examples per table) was brittle and labor-intensive — only previously modeled cases benefited, unanticipated questions still failed.

## Contribution
- A semantic mediation layer (controlled augmentation mechanism) that transforms brief, goal-oriented prompts into database-grounded inputs without burdening users with schema knowledge or operational overhead. Three requirements: (1) preserve user intent (no critical meaning altered or lost), (2) knowledge grounded (enrich prompts with domain + data semantics), (3) lightweight (automatic, low-maintenance).
- Two design variants compared: schema-based mediation (retrieve relevant table schemas by semantic similarity — lightweight baseline) vs KG-based mediation (knowledge graph automatically constructed from the database schema — tables + columns as nodes; has_column edges + joins_on edges inferred from PK-FK constraints or name-matching/type-compatible heuristics; captures direct and indirect joins; graph traversal for connected tables/columns).
- Design principle (DSR Aim/Context/Mechanism/Rationale): LLM-based enterprise data assistants should incorporate a KG-based mediation layer that operates on and augments user prompts, reducing dependence on manual prompt engineering and bridging user goals with system representations.

## Method (core)
- KG auto-built with NetworkX 3.5 from Databricks Information Schema: 273 nodes, 540 edges on the partner database; nodes stored in ChromaDB 1.3.4 with OpenAI text-embedding-3-large (semantic matching of user phrasing to canonical KG nodes). Deliberately no domain constructs (specialized metrics, fine-grained filters) — isolating the contribution of structural database knowledge.
- 3-step pipeline: (1) segment the user prompt into distinct intent units; (2) similarity_search per segment -> entry nodes; retrieve table->all its columns and column->parent table; (3) traverse the KG for direct and indirect join relationships -> subgraph (average 54 nodes SD=30, 99 edges SD=41 per query) -> LLM prompt refinement (GPT-4.1 or Claude Sonnet 4) integrating retrieved knowledge and join specifications. Schema-based baseline: retrieved schemas averaged 91 columns (SD=19).
- Evaluation on real enterprise logs: N=158 interactions from N=29 CFO-unit users (last 30 days; assistant live 6 months but only 30 days of logs stored). Two complementary approaches: LLM-as-a-Judge binary Completeness (COMPLETED/NOT COMPLETED after Alabool 2025, 3 few-shot examples, Pydantic-enforced structured output) and human validation (2 partner data analysts, 2 iterations — first analyst reviews, second reviews those results, compare/discuss/resolve conflicts -> TP/FP/FN -> Precision/Recall/F1). TN control checks with non-database prompts; preliminary end-to-end trial on a random subset of 30 interactions.

## Key Findings
- GPT-4.1: KG Precision 90.67% (Schema 69.05%, +21.62pp), Recall 88.31% (Schema 73.11%, +15.20pp), F1 89.47% (Schema 71.02%, +18.45pp); Completeness 93.04% (Schema 89.24%, Baseline 91.14%) — KG preserves intent BETTER than the no-mediation baseline despite exposing additional database content.
- Claude Sonnet 4: KG Precision 87.23% (Schema 75.17%, +12.06pp), Recall 93.52% (Schema 92.56%, +0.96pp), F1 90.29% (Schema 82.17%, +8.12pp); Completeness 86.45% (Schema 84.52%, Baseline 85.33%).
- Annotator agreement: 98.73% (KG) / 98.10% (Schema) for GPT-4.1; 95.57% (KG) / 96.84% (Schema) for Claude Sonnet 4.
- Processing time: schema-based 1.1s average vs KG-based 2.7s; KG retrievals averaged 54 nodes (SD=30) + 99 edges (SD=41) per query; mediated prompts longer (GPT-4.1 M=29-30 vs baseline M=18 words; Claude M=33-37 vs M=17) because KG surfaced explicit, mostly correct join specifications.
- Demo ("Which audit requests and findings still need to be completed, including company name and ID?"): KG-based mediation correctly identifies audit_single_issues.issue_done=FALSE and joins basis_info on unit_id (21 nodes, 30 edges); schema-based identified the same 3 tables and 76 columns but selected wrong ones -> wrong prompt "Search the audit_status table for the value of P8A_AUDIT_NAME" (audit-period level instead of individual requests + companies).
- Preliminary end-to-end test (30 interactions): true-positive mediated prompts proceeded without additional schema discovery (lower latency); FN cases needed explicit schema lookup or returned correct-but-broader results requiring narrowing; higher F1 correlates with higher end-to-end accuracy; schema-based mediation was more prone to erroneous/hallucinated joins on complex schemas — once encoded in the mediated prompt, downstream query planning and execution reliably failed.
- TN control checks: neither approach injected additional or incorrect knowledge for non-database prompts.

## Actionable Insights
- Before opening data assistants to non-SQL business users, install an auto-built KG-mediated prompt augmentation layer (273 nodes/540 edges built in minutes) instead of manual per-table few-shot curation: Precision +12-21.6pp, F1 +8.1-18.5pp across two LLMs. E.g. a sales assistant answering "which orders are still undelivered for VIP customers" gets the right tables + joins injected automatically instead of guessing.
- Schema-similarity retrieval alone is a trap on complex multi-join schemas: hallucinated joins, once encoded in the prompt, make downstream execution reliably fail. E.g. a dashboard query needing a 3-table join — schema-only may return a wrong join path and silently wrong results; KG traversal (direct + indirect paths) is the minimum safeguard.
- "Just-right" context beats large context windows: a compact subgraph (~54 nodes/99 edges) outperforms flooding, and mediation does not degrade completeness (93.04% > baseline 91.14%). E.g. prompt-refinement pipelines should inject a compact subgraph rather than the full schema.

## Assumptions & Limitations
- Conditions: database schema metadata available (information schema) with PK-FK constraints or sufficient name/type heuristics for joins_on edges; embedding quality adequate to map user phrasing to canonical nodes ("reliable KG performance depended on identifying the right entities and relations" — the database must be thoroughly curated); enterprise LLM assistant context.
- Authors admit: single-enterprise setting (one partner's CFO unit), 158 interactions/29 users limits generalizability; simulation-based evaluation on log-data validated by human annotators rather than real-time user input (next design cycle: field deployments, A/B studies); KG coverage requires systematic governance in production (versioning, change management); KG auto-generation excludes domain constructs (metrics, filters) by design; network density not systematically varied; graph structure differs across domains; minimal-change mediation cases (knowledge gaps) not captured by the completeness metric.
- Not stated: single LLM-as-Judge bias mitigated only with 3 few-shot examples (no multi-judge ensemble); binary completeness label is coarse; end-to-end test is informal (30 samples, no statistics); only local processing latency reported (1.1s vs 2.7s) — mediation inference COSTS not reported; paper prose cites "85.33%" for GPT-4.1 schema completeness but the table shows 85.33% is the Claude baseline (GPT-4.1 schema = 89.24%) — possible paper typo, table values used; OpenAI embedding model sends enterprise data externally (privacy consideration for data lakes).
